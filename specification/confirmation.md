# The owner's confirmations

This file records what the owner confirmed of Regula's specification, in the owner's words.

## 2026-11-01

The owner added a constraint over all Regula work and confirmed the restatement that follows, which the owner's delegated agent wrote. The agent decided on the owner's behalf that the README states being the most trusted linter as an aim, because the restatement allows no superlative in public until the proofs back it, and that the constraint stays a written rule with no enforcement in code, because a violation is caught at review and is easy to undo. Neither decision is the owner's confirmation.

> Regula is meant to be to Lean linters what seL4 is to kernels: the most trusted one, because its claim is exact and proved. Simplicity is how that becomes achievable, as in LionsOS, where each component does only the minimum its use case needs.
>
> - Removal comes first: before adding or repairing anything, ask whether it can be deleted, or its input narrowed, so the need goes away.
> - Hard proofs are a warning: a proof far harder than the code it covers means the code should get simpler, not only better proved.
> - Simplicity never replaces proof: RG1001 to RG1006, the two verdicts and "no bugs" all stand.
> - One use case: one toolchain, one way to run it, a closed input, and a truthful refusal for anything else. Refusing something outside a narrow published contract is not a false refusal.
> - An seL4-style claim: exactly what is proved, for which inputs, under which listed assumptions, with no superlatives in public until the proofs back them.
> - The work follows it too: the simplest analysis that answers the question, with no frameworks.
>
> For example, this rules out adding 1,000 lines to keep an unusual folder layout working, adding a mode to avoid a refusal, or keeping a tool in the repository for one analysis. It still allows a long proof of something truly hard, such as the two-way axiom rules.

### What no false refusal means

Later on 2026-11-01 the owner answered "Yes, as recommended" to a restatement of what "no false refusal" means, which the owner's delegated agent wrote after an analysis the owner asked for. In substance: Regula stops trying to prove that a project matching a description is owed a pass, because that description was tied to real files only by assumptions. `Project.config` and `SourceFile.read` were chosen values, seven of the thirteen fields of `Answers` restated the conclusion for a case of `Reason`, and Lake's loader depends on axioms outside Regula's own profiles (10 for `Lake.loadTomlConfig`, 75 for `Lake.loadWorkspaceRoot`), so no correspondence with it can be proved under them. Instead Regula publishes a closed list of refusals. Each refusal is proved true of what Lean, Lake or the operating system answered, and a project passes when no refusal applies and the rules hold. So "no false refusal" means that a refusal is never untrue, not that every reasonable project passes, and "exit 0 exactly when" is withdrawn. Newly refused, each with a true message: a default executable, including the `lake new` application template; a `srcDir` on a target; and a source directory with a space or a non-ASCII name.

The owner kept in force that the false-pass guarantee does not weaken: what a pass rests on stays proved over the actual program with the same three axioms, and a project with no refusal, on which the rules hold, passes, so a program that refuses everything does not meet the contract. The owner's confirmed examples keep their verdicts, and H1 to H5 stay as stated hypotheses, re-read at each upgrade. Where simplicity outranks the full verdict stays open with the owner, and this revision holds on every branch of that question.

So `Project.InDomain`, `Configuration`, `Answers`, `LakeAgrees`, `DomainRun`, `domain_owed`, `reason_excluded`, `reason_classified`, `run_plain_exit_zero_iff`, `run_full_exit_zero_iff`, `plain_exit_zero_owed`, `full_exit_zero_owed`, `OwedExact` and `OneContext` are gone, and the commit `2c9524b0` holds them. The list is [in the specification](README.md#the-closed-list-of-refusals).

### The language check

On 2026-10-31 the owner answered "Yes, as recommended" to a restatement of what the check must do, with its cases. The words that follow are the restatement, which the owner's delegated agent wrote after reading Regula's code, the code of two other projects of the owner's and an early prototype of this check, and which the owner adopted. So the second reading below starts from words that the code influenced.

> Before anything is compiled, the check reads every Lean file Lake would compile for the claim, and the project's Lake configuration. If it passes, then while Lake builds those files no code written in the project runs, and no file installs anything that replaces what the compiler runs for a definition. So what the build contains came from Lean's own elaborators acting on source the check read. Whatever it cannot read or does not recognize is refused, including any construct a later Lean adds. An empty set of files is `incomplete`, never a pass. It leaves unsaid what a theorem's statement means to a reader, what another process does, and anything about a dependency's code.
>
> For example, it refuses `run_cmd`, `#eval`, `#guard`, `run_tac`, `by_elab`, `native_decide`, `decide +native`; `macro`, `syntax`, `notation`, `elab`, `initialize`, and `@[local macro k]` on a plain `def`; `lakefile.lean`, and a plugin in Lake's TOML. It admits Regula's own core, and library code using `simp`, `omega`, `decide +kernel`, `variable` and `deriving DecidableEq`. These examples are witnesses of the criterion, not its boundary.
>
> A hypothesis about Lean's behaviour, written in the specification and re-read at each Lean upgrade, counts as Lean staying trusted. So "no bugs" here means no bug outside stated, version-bound claims, and the hypotheses are named wherever a pass is described.
>
> A build importing Mathlib runs Mathlib's code when it imports it, so the check cannot make its promise there. Every build gets a proof verdict, meaning the proofs are sound and use allowed axioms; only a build with no Mathlib in its imports gets the full verdict. Regula's output says which it gave, so neither can be mistaken for the other.
>
> The decision itself is a pure function over the parser's output, proved in both directions against a specification written first and independently of the code. It stays only if it can be proved: if it cannot meet that bar, the result is to say so plainly, not to weaken it. The code is the model of how such code is written. No rule is weakened, and nothing is released from this change alone unless the owner's remaining conditions hold.

### The language check

On 2026-10-31 the owner answered "Yes, as recommended" to a restatement of what the check must do, with its cases. The words that follow are the restatement, which the owner's delegated agent wrote after reading Regula's code, the code of two other projects of the owner's and an early prototype of this check, and which the owner adopted. So the second reading below starts from words that the code influenced.

> Before anything is compiled, the check reads every Lean file Lake would compile for the claim, and the project's Lake configuration. If it passes, then while Lake builds those files no code written in the project runs, and no file installs anything that replaces what the compiler runs for a definition. So what the build contains came from Lean's own elaborators acting on source the check read. Whatever it cannot read or does not recognize is refused, including any construct a later Lean adds. An empty set of files is `incomplete`, never a pass. It leaves unsaid what a theorem's statement means to a reader, what another process does, and anything about a dependency's code.
>
> For example, it refuses `run_cmd`, `#eval`, `#guard`, `run_tac`, `by_elab`, `native_decide`, `decide +native`; `macro`, `syntax`, `notation`, `elab`, `initialize`, and `@[local macro k]` on a plain `def`; `lakefile.lean`, and a plugin in Lake's TOML. It admits Regula's own core, and library code using `simp`, `omega`, `decide +kernel`, `variable` and `deriving DecidableEq`. These examples are witnesses of the criterion, not its boundary.
>
> A hypothesis about Lean's behaviour, written in the specification and re-read at each Lean upgrade, counts as Lean staying trusted. So "no bugs" here means no bug outside stated, version-bound claims, and the hypotheses are named wherever a pass is described.
>
> A build importing Mathlib runs Mathlib's code when it imports it, so the check cannot make its promise there. Every build gets a proof verdict, meaning the proofs are sound and use allowed axioms; only a build with no Mathlib in its imports gets the full verdict. Regula's output says which it gave, so neither can be mistaken for the other.
>
> The decision itself is a pure function over the parser's output, proved in both directions against a specification written first and independently of the code. It stays only if it can be proved: if it cannot meet that bar, the result is to say so plainly, not to weaken it. The code is the model of how such code is written. No rule is weakened, and nothing is released from this change alone unless the owner's remaining conditions hold.

The owner's delegated agent amended this on 2026-10-31, on a report that a `lakefile.lean` runs when `lake lint` loads the workspace, before the check starts, so it can act and delete itself, and a full verdict could then be forged. That contradicts the purpose of the restatement. So a full verdict comes only from a checker started from outside the checked project's Lake, built independently of that project and given its path, which reads the configuration by name before any Lake load of the project, and `lake lint` inside a project gives only the proof verdict. As a consequence Regula's own program gets a full verdict on itself from a checker built beforehand from a separate copy. The same agent decided that a dependency with no Mathlib whose files fail the check, or that has a `lakefile.lean`, leaves the build at the proof verdict, and that the check's rule identity is one no released version used for another meaning. None of this is the owner's confirmation.

The owner's delegated agent amended this again on 2026-10-31, after a review found that fetching and classifying dependencies before admission let a manifest act on a path outside the project, that a Lake load with no manifest ran a dependency's configuration, and that the checker's reader lay outside what a full verdict read. A full verdict now requires a project with no dependency at all, read from its Lake configuration before any Lake load. Any `require` leaves only the proof verdict, and the checker fetches and runs nothing of a project's dependencies: it says that only a proof verdict is possible and exits with 3, and the operator gets that verdict with the three commands in the project. Of the checker, everything that does not call Lake is inside Regula's default targets and so inside its own full verdict, and what calls Lake only calls Lake and is named in the trusted base. This replaces the earlier statements of this record that Regula's own program gets a full verdict on itself, and that a dependency with no Mathlib leaves the build at the proof verdict by the check of its files: no dependency's file is read any more. This amendment is the agent's and no confirmation of the owner's. The restatement that the owner confirmed leaves unsaid anything about a dependency's code and says that every build gets a proof verdict, which the three commands still give.

# Specification of Regula

Regula exists to be trusted, and to be the example of how Lean 4 code should be written: well factored, well designed, following best practice, and formally proven. Its owner decided on 2026-10-31 that being free of bugs outranks every lint rule and feature, so Regula gives up any rule, feature or package it cannot prove rather than patching it, documenting a limit or keeping a stated gap. Only Lean, its kernel and Lake's own behaviour are meant to stay trusted; Regula's own code is meant to be proved, or so thin that it only calls Lean. [The trusted base](#the-trusted-base) states what this revision rests on, and [the run of the checker](#the-run-of-the-checker) what is proved of its effects.

This document states what Regula's checks are, what each is proved to do, and what stays assumed. It follows the order that the owner chose: first a small proved core, then [a check](#the-language-check) that reads each source file before anything is compiled and refuses anything outside a closed set of allowed constructs. [The confirmation record](confirmation.md) holds the owner's words.

## How to read this document

Each claim about Lean, Lake or the theorems of this package has one of four marks:

- **Proved**: Lean checks a theorem of the Lean package in this directory. The theorem name follows the mark.
- **Measured**: an observation on the pinned toolchain, with its procedure.
- **Assumed**: a statement about Lean, Lake or the operating system that no proof here examines.
- **Open**: an obligation that this document does not discharge.

A statement of what a rule or the checker must do is specification, and it has no mark. A citation such as `Lean/Meta/Native.lean:45` is a path below `src/` of the tag `v4.35.0` of Lean, the toolchain that `lean-toolchain` pins, and one that starts with `Lake/` is a path below `src/lake/` of that tag. To check all statements and theorems, run `lake build --wfail` in this directory. The Lean library `RegulaSpecification` requires lean-intent at the commit that `lakefile.toml` names, and the root package.

## The shape of a rule

Each rule is a pure function from the closed input to the constants that it reports. Its formal statement is a lean-intent intent record (`LeanIntent.IntentRecord`), built by `ruleRecord` in [`RegulaSpecification/RuleRecord.lean`](RegulaSpecification/RuleRecord.lean). The record has one property: on each well-formed input, the function reports a subject exactly when the subject violates the rule. Thus the meaning of a rule is all in its violation predicate, for example `Violates1005`.

For each rule, the package gives a case that the rule must refuse and a case that it must admit (`Witnessed`). From them, it proves that the record meets lean-intent's obligations O2 (at confirmation and before a run), O3, O4, and O5 with the freedom `SameReports`, which is the order and the repetition of the reported subjects. A rule's function takes the proof of the closed form with its input (`Checker`), so the record has no case for an input that the admission refuses. **Proved**: `adequate`, applied in `rg1001_adequate` and the theorems that follow it. O1 holds for each record. **Proved** by lean-intent: `LeanIntent.o1_wellTyped`.

Each rule function that the checker runs is proved against its record in [`RegulaSpecification/Proofs/`](RegulaSpecification/Proofs/). The functions run over `Regula.Closed.Input`, so the proofs are about the executed definitions, not about a copy of them.

These theorems have no hypothesis about the input or about the tables that a rule reads, because the types carry them. A value of `Regula.Closed.Input` has the closed form (**proved**: `wf_toSpec`), and a value of `Regula.Closed.Tables i` holds what each table holds of the input `i`, so `rgN_exact` holds of every value of that type. A rule computes an axiom set from the input itself, by a search backwards from each axiom through the constants that each constant mentions (`Tables.axiomSet`), and that set is exactly what `Input.AxiomOf` states (**proved**: `Tables.mem_axiomSet`, `axiomSet_iff`, with `mem_reach`). The checker no longer calls `Lean.collectAxioms`, so nothing about that function is assumed.

## The closed input

The closed input is the type `Input` in [`RegulaSpecification/Input.lean`](RegulaSpecification/Input.lean):

| Field | Owner and interface |
| --- | --- |
| `profile`, the profile that the project states | The one argument of the lint driver, `lintDriverArgs` of the project's Lake configuration |
| `modules`, the claimed modules | Lake's load gives the modules of the default targets of the root package; each loaded module whose `.olean` lies in the root package's library directory is claimed |
| `decls`, each constant of the environment | `Lean.importModules` with `loadExts := false`, at the level `.private` |
| `unique`, that no name is that of two constants | The loader's proof, from the keys of the hash map that holds the constants (`Std.HashMap.distinct_keys_toList`) |

The input has no source text, message, compiled code, option or build log. A rule does not decide what it cannot read in this input.

The admission refuses an input that does not have the closed form (`Input.WellFormed`). Each constant that a constant mentions is held (**proved**: `open_mention_refused`). At least one module is claimed, so a claim of nothing is not read as a pass (**proved**: `no_claim_refused`). **Proved**: `admit_ok_iff` for the function that the checker runs, `Draft.admit`, which gives the proofs of both to the type that the rules read.

What the type excludes needs no check. The type `Input` of this package cannot hold a name twice, as an environment keeps its constants in a hash map, and the checker's `Facts` carries that its modules are those of the environment's header, so a claimed module is a loaded one (**proved**: `claimed_loaded`). `Safety` cannot state a constant that is both unsafe and partial, which Lean does not make (**proved**: `not_unsafe_of_partial`). `Regula.Closed.Report` cannot state a pass with a finding, a failure with none, or an incomplete run with no reason.

The shell has three effects on the plain `lake lint` path: it loads the build, it prints its report, and it sets its exit code. It writes no file there. It runs no initializer of the loaded modules, because it loads them without extension states. Lake's own load of the workspace on that path runs Git in the environment of the caller. The full gate takes another path: it loads the root package's configuration alone, which resolves no dependency, and has more effects, which [the language check](#the-language-check) gives: it reads source files and copies them to a tree of its own, which it removes afterwards, it imports the toolchain's modules with their initializers to parse those files, and for an admitted project it runs `lake build --wfail` and `lake check` in that tree. [The run of the checker](#the-run-of-the-checker) states these effects.

## From a build to the input

`Regula.Load.Facts.input` is the pure function that fills the input from an environment, and [`RegulaSpecification/Proofs/Load.lean`](RegulaSpecification/Proofs/Load.lean) states what it gives. So a later change to the loader that drops a constant, a field or a mention fails the gate's build of this package.

- **Proved**: `pass_iff`. For every environment, every `Facts` and every profile, when the loader gives an input, the checker passes on it exactly when the environment has `EnvForm` and `EnvFloor`. These two statements name no field of the input. `EnvForm` is the closed form. `EnvFloor` states RG1001 to RG1006 of each constant of `Environment.constants.map₁` in a claimed module. What a name mentions, and whether it names an axiom, is read from the fields of the `ConstantInfo` that `map₁` keeps and of each constant of that name that a loaded module's own data states (`EnvMentions`, `EnvAxiom`, `mem_usesIn`, `mem_stated`).
- **Proved**: `pass_floor`, the same on the path that the shell decides (`Regula.Closed.decision`). A pass also states that each module of a default target is claimed, that each claimed module is loaded, and that each constant of the environment has a module. `input_form` states the closed form of each environment that the loader gives an input for.
- **Proved**: `pass_held`. On a pass, each constant of a claimed module, as that module's own `.olean` states it and also when Lean's import replaced it (below), is no axiom, is partial and not unsafe when it has either flag or a recursion helper's name, has no value that mentions a loop construct, and reaches through what it mentions only axioms that the profile admits. That theorem does not state the rest of the helper's form of such a constant; `pass_iff` states it of the constant that `map₁` keeps.
- **Proved**: `decision_pass`, `decision_failed`, `profileOfRun_ok` and `profileOf_eq_some`, for the shell's pure decisions. `mem_claimed_place`, `toolchain_place` and `below_iff`, for what the places of the modules decide, and `moduleOf?_eq` for the module of a constant. `dispatchedFrom_iff`, for the workspace that Lake dispatched.

Each field of the input, with the rules that read it, its statement against the environment, and what that leaves about Lean or Lake:

| Field | Read by | Statement | Left assumed |
| --- | --- | --- | --- |
| `profile` | RG1005 | `Loaded.profile`, `profileOfRun_ok`, `profileOf_eq_some` | Lake passes `lintDriverArgs` as the arguments |
| `modules` | each rule, the admission | `Loaded.modules`, `Loaded.roots`, `claimed_loaded`, `mem_claimed_place`, `below_iff` | Lake names the modules of the default targets and the root package's library directory; `findOLean` finds each `.olean` on Lake's search path |
| `decls`, and each `name` | each rule, the admission | `Loaded.sound`, `Loaded.whole`, `Facts.decls_nodup`, `mem_stated` | `map₁` holds the constants that the import keeps, and `header.moduleData` what each `.olean` states |
| `module` | each rule | `Loaded.sound`, through `Facts.info?`, `moduleOf?_eq` | `getModuleIdxFor?` and `header.moduleNames` name a module that holds the constant |
| `kind`: `axiom` when any loaded module's own data states an axiom of the name, otherwise the constructor of the constant that `map₁` keeps | RG1001, RG1002 to RG1005, RG1006 | `kind_axiom`, `kind_definition`, `kind_envAxiom`, `isAxiom_env`, `mem_stated` | the `ConstantInfo` that each `.olean` holds |
| `safety` | RG1006 | `pass_iff`, through `EnvFloor`, `safetyOf_partial`, `safetyOf_safe`, `not_unsafe_of_partial` | as for `kind` |
| `uses`: what the constant that `map₁` keeps mentions, and what each constant of the name that a loaded module's own data states mentions | RG1002 to RG1005, the admission | `mem_usesOf`, `mem_usesIn`, `mem_stated`, `reaches_env` | `Expr.getUsedConstants` lists each constant of an expression |
| `valueUses` | RG1006 | `mem_valueUsesOf` | as for `uses` |
| `implementedBy`, `isExtern` | RG1006 | `helper_env` | `getImplementedBy?` and `isExtern` read the module entries under `loadExts := false` |
| `inToolchain` | RG1003, RG1005 | `known_env`, `toolchain_place`, `below_iff` | Lean finds the toolchain's library only below its `lib/lean` directory |

No field is left for removal: each has a statement against the environment. What remains assumed of a field is Lean's or Lake's behaviour. That a run passes what they returned to `Facts.input` is proved (`BuildRead`, `Loaded`, `run_meets`).

**The constants that Lean's import replaces.** Lean refuses two imported modules that declare one name with different values, with one exception. It merges two theorems of one name and type, a theorem with an axiom of that name and type, and two such axioms, and it keeps one constant under the name of the first module that holds it (`subsumesInfo` and `finalizeImport`, `Lean/Environment.lean:2269` and `2336-2345`). So the merged environment can hide an axiom or a chain of mentions that a loaded module's own data states, in a claimed module or a dependency. **Measured** on 2026-10-31 at pull request 515, on a project of `kernel-only`: a module whose theorem `shared` used `Classical.choice`, beside a module whose theorem `shared` had the same type and a proof with no axiom, passed `lake build --wfail`, `lake check` and `lake lint`. Lean regenerates a definition's equation lemmas in each module that needs them, so refusing each such constant would refuse ordinary projects (**measured**: `f.eq_def` in two modules). So the loader reads the own constants of every loaded module from the header of the environment, claimed or not (`Facts.stated`), and what any of them mentions, and whether it is an axiom, counts for its name. On a pass, each axiom reached from a constant of a claimed module, by following mentions that any loaded module's own data states, is one that the profile admits (**proved**: `pass_floor`, `pass_held`, `mem_stated`). So a replaced dependency theorem's mentions now count, and so does a dependency's axiom that a theorem replaced, and this can refuse a build whose merged environment is clean. A constant of a claimed module that the environment does not show to the rules must also be a theorem, with neither flag and no recursion helper's name (`fitsUnshown`), whose value mentions no loop construct, and whose mentions reach only axioms that the profile admits, or the run is `incomplete` (`Facts.claimedConstants`, `Facts.unread?`). **Measured** on 2026-10-31 on this change, before it took in pull requests 516 and 518, on disposable projects, each after `lake build --wfail`: the project above gives `incomplete` or `fail` by the order of its imports, and passes under `standard-logical`. Under `kernel-only`, a module that mentions a dependency's theorem `bridge` whose proof uses `Classical.choice`, beside a claimed module whose `bridge` uses no axiom, gives `fail` (RG1005). With a theorem `shared` that mentions `bridge` and that the second module also replaces, it gives `incomplete`, and it passes under `standard-logical`. A module that mentions a dependency's axiom `x`, beside a claimed module with a theorem `x`, gives `fail` (RG1003, RG1005) under `kernel-only` and under `standard-logical`. When the dependency's `bridge` uses no axiom, the `kernel-only` project passes, and so do the two modules with `f.eq_def` under `standard-logical`.

## The rules

### RG1001 to RG1005: the foundation profile

Each reads a constant of a claimed module. RG1002 to RG1005 read its transitive axiom set `Input.AxiomOf`, which the rules compute from the input (`axiomSet_iff`). The four refine one refusal: each axiom that RG1002, RG1003 or RG1004 names also violates RG1005 for each profile. Thus a wrong choice between these rules changes the rule of a finding, but not the verdict. **Proved**: `rg1005_of_hole`, `rg1005_of_unknown` and `rg1005_of_compiler`. The formal statements are in [`RegulaSpecification/Foundation.lean`](RegulaSpecification/Foundation.lean).

- **RG1001: project axioms.** A constant of a claimed module has the kind `axiom`. An assumption is a hypothesis or a field of a structure, so that each theorem that uses it shows it in its type. `lake check` refuses an axiom only when a constant mentions it, so it does not do the work of this rule. `Violates1001`.
- **RG1002: proof holes.** A constant depends on `sorryAx`, directly or through an import. `Violates1002`.
- **RG1003: unknown axioms.** A constant depends on an axiom other than `propext`, `Quot.sound` and `Classical.choice` of the toolchain, and RG1002 and RG1004 do not name it. `Violates1003`, with `Input.Known`. **Assumed**: Lean finds the library of the toolchain only below the `lib/lean` directory of the pinned toolchain, which the shell reads to say that a module is in that library.
- **RG1004: native proofs.** A constant depends on an axiom with the name form `<declaration>._native.<tactic>.<suffix>` that `native_decide`, `decide +native` and `bv_decide` add (`Lean/Meta/Native.lean:45` and `75-82`), or on an axiom by which the kernel trusts the compiler, of which `v4.35.0` declares none. `Violates1004`, with `NativeProofAxiom` and `compilerAxioms`. **Measured**: `native_decide` gave `n._native.native_decide.ax_1_1`. The rule identifies the axiom by its name, so an author can give an axiom that name. Then RG1004 reports it in place of RG1003, and the verdict is the same.
- **RG1005: the profile.** A constant depends on an axiom that the project's profile does not admit. Kernel-only admits no axiom. Choice-free admits `propext` and `Quot.sound`. Standard-logical also admits `Classical.choice`. Each admitted axiom is the toolchain's own. `Violates1005`, with `Input.Admits`.

### RG1006: `unsafe` and `partial` declarations

The rule refuses three things in a claimed module: an `unsafe` or `partial` constant without the form of Lean's recursion helper, a constant with a helper's name without that form, and a constant whose value directly mentions a loop construct of Lean. `Violates1006`, with `Input.RecursionHelper`, `HelperNamed` and `MentionsLoop`, in [`RegulaSpecification/Safety.lean`](RegulaSpecification/Safety.lean). **Proved**: `rg1006_exact` in both directions, `rg1006_checker_refuses_loop` for each construct, and `rg1006_checker_refuses_forged_name` for a plain definition with a helper's name.

**The loop constructs.** The class comes from Lean's `Init/While.lean`. A `while`, `repeat` or `repeat ... until` needs no `partial` of the module that uses it, because it compiles through `Lean.Loop.forIn` to `repeatM`, whose body is a private `partial` of that file. So the flags alone do not show a loop that does not end. The rule reads the value of each claimed constant for the one value of the type `Lean.Loop`, `Lean.Loop.mk`, and for `repeatM` (`loopConstructs`). `termination_by` and `partial_fixpoint` stay allowed, and so does `for` over a list. The owner's delegated agent added this on 2026-10-31, after `while true` passed all three commands while a `partial def` of the same loop failed.

**Measured** on 2026-10-31 on a disposable project: `while`, `repeat`, `repeat ... until`, a direct `repeatM`, a direct `Lean.Loop.forIn ⟨⟩`, `forIn Lean.Loop.mk` and an `Inhabited Lean.Loop` instance were each refused; `termination_by`, `partial_fixpoint` and `for` over a list passed.

What this leaves out, as accepted risk under the owner's trust in dependencies:

- A loop inside a dependency or the toolchain, such as `IO.iterate` (`Init/System/IO.lean:780`), which is a `partial def` that a claimed constant can call. **Measured**: it passes.
- A claimed function that takes a value of `Lean.Loop` as an argument mentions neither construct, and it passes (**measured**). Running it needs that value, which claimed code can make only through `Lean.Loop.mk`, so only a dependency's value runs it.
- A mention only in a constant's type, which runs nothing. **Proved**: `rg1006_admits_type_mention`.
- A loop that a claimed module's own code adds during the build, with the forged helper below.

**The recursion helper.** The form is a partial constant `f._unsafe_rec`, not unsafe, with no `implemented_by` and no `extern`, in the module of a safe, total definition `f` with neither. Lean makes the base of a `partial def` an opaque constant, so the rule reports the helper of a `partial def`.

**A helper's name.** The compiler reads `f._unsafe_rec` in place of `f` by its name alone, whatever its kind and flags (`getDeclInfo?`, `Lean/Compiler/LCNF/ToDecl.lean:25-27`). So the rule refuses each constant of a claimed module with a name of the form `b._unsafe_rec` that has not the helper's form, and each such constant that is not partial in particular, for each kind and however it was declared. **Proved**: `rg1006_reports_named_not_partial`. Only a definition can be partial (`ConstantInfo.isPartial`, `Lean/Declaration.lean:463-465`), so each constant of another kind with that name is refused. The checker runs the compiler's own test, `Lean.Compiler.isUnsafeRecName?`, in place of a copy of it. **Proved**: `isUnsafeRecName_eq` states that test against `HelperNamed`, and `mkUnsafeRecName_eq` states the name that `getDeclInfo?` looks up, so a toolchain with another form fails these proofs. **Assumed** from the source: the compiler's only readers of a helper by its name are `getDeclInfo?`, `declIsNotUnsafe` and `toDecl` (`Lean/Compiler/LCNF/ToDecl.lean:27`, `37` and `51`), with `toLCNF`'s check of `isNoncomputable` and its `replaceUnsafeRecName` (`Lean/Compiler/LCNF/ToLCNF.lean:448` and `525`). The owner's delegated agent added this on 2026-10-31, after an audit found that the plain definition below passed the rule.

```lean
def g (n : Nat) : Nat := n
def g._unsafe_rec (n : Nat) : Nat := n + 1
theorem g_one : g 1 = 1 := rfl
```

**Measured** on 2026-10-31. Before this rule, at the commit of the cut, that module passed `lake build --wfail` and `lake lint`, while `#eval g 1` and `lean --run` of `g 1` printed `2`. Lean also panics on this input during a Lake build (`emitCForDecls`), and Lake prints the panic as information and exits 0, so `--wfail` does not catch it. Now `lake build --wfail` and `lake check` still pass it, and `lake lint` reports RG1006 and exits 1. On a disposable project, RG1006 reported the helper's name in each of these forms: `def`, `abbrev`, `opaque`, `instance`, `theorem`, `axiom`, `inductive`, `structure`, `class`, a constructor, a structure field, `where`, `let rec`, `namespace`, a quoted name, `private`, `protected`, `noncomputable`, `@[reducible, inline]`, `@[extern]`, `@[implemented_by]`, a `macro` that expands to a `def`, a `mutual` block, a recursive `def`, a top-level `_unsafe_rec`, a `partial def` with and without recursion, an `unsafe def`, and a `module` file with `public` and `private` declarations. Lean itself refused `initialize` and `syntax (name := ...)` with that name, and a `mutual` block of a `def` and a `partial def`.

**Measured** on the same day: structural and well-founded recursion, each in a `mutual` block too, nested recursion through `where`, `let rec`, `private`, `protected`, an `abbrev`, a method of an instance, `partial_fixpoint`, `@[specialize]`, universe polymorphism, a `module` file, and the functions that `deriving Repr, BEq, Hashable, DecidableEq` writes for a recursive type all gave a helper that passed `lake lint`, and that project passed `lake build --wfail` and `lake check`. The rule still reports the helper of what `deriving` writes as a `partial def`, as it did before, because the base is an opaque constant (`usePartial`, `Lean/Elab/Deriving/Util.lean:116`). **Measured**: `Repr` and `BEq` on a nested inductive type and `Ord` on a recursive type.

The rule checks the helper's form and nothing about what the helper computes. **Known gap of the proof verdict**: a claimed module can forge a helper of the true form through its own code during the build, such as `run_cmd`. The full verdict closes this, because [the language check](#the-language-check) refuses that code before it can run. Lean's declaration forms give a partial definition only through `addAndCompilePartialRec`, which names the helper after the definition it compiles (`Lean/Elab/PreDefinition/Basic.lean:280-292`), so a form with no code of the project's own gives no such pair. That last sentence is read from the source and has no theorem. **Measured** on 2026-10-31 with this revision of the checker, on a project of one module:

```lean
import Lean
open Lean Elab Command
run_cmd liftCoreM do
  let ty := mkForall `n .default (mkConst ``Nat) (mkConst ``Nat)
  let val := mkLambda `n .default (mkConst ``Nat) (mkApp (mkConst ``Nat.succ) (mkBVar 0))
  addDecl (.defnDecl { name := `g._unsafe_rec, levelParams := [], type := ty, value := val,
                       hints := .opaque, safety := .partial, all := [`g._unsafe_rec] })
def g (n : Nat) : Nat := n
theorem g_one : g 1 = 1 := rfl
#eval g 1
```

The `#eval` printed `2` while `g_one` holds, and `lake check` and `lake lint` both passed. ## What a pass means

Regula gives one of two verdicts, and the last line of a run says which. This section is about the proof verdict. [The language check](#the-language-check) states the full verdict, which needs what a pass here needs and more.

A pass of the proof verdict is the result of three commands of the pinned toolchain on one finished build, in this order:

1. `lake build --wfail`.
2. `lake check`. On macOS it is `lake check --inadvisably-no-sandbox`, and it prints that the run is not trustworthy.
3. `lake lint`, Regula's checker.

The first two are Lean's own, and Regula makes no claim of its own about what they decide. **Assumed** from the source: `lake check` builds the default targets, exports them and replays the export with `leanchecker` in a process that loads no `.olean` file of the project (`Lake/CLI/Main.lean:1218-1226`, `Lake/CLI/Check.lean`), and it refuses each axiom other than the three that a constant of the export mentions (`Lake/CLI/Check.lean:662-675`, `Lake/Check/Axioms.lean:57-71`).

Such a pass means that the proofs of the claimed modules are sound and use only axioms that the profile allows. It says nothing about what a compiled program runs. A claimed module can change that with `@[implemented_by]`, `@[extern]` or `@[csimp]`, which no rule reads, or with a helper of the true form that its own code adds during the build, whose form RG1006 reads and whose value no rule reads. **Measured** on 2026-10-31: a module with each of the first three passed all three commands.

The checker alone means less, because it reads what the build holds and replays nothing. **Measured** on 2026-10-31: a module that added a theorem of `False` with `set_option debug.skipKernelTC true` passed `lake build` and `lake lint`, and `lake check` refused it.

`lake check` imports the modules of the default targets into one environment, and the checker does too. So a project of two default executables that each declare `main` fails both commands. Lean refuses two imported modules that declare one name with different values (`Lean/Environment.lean:2336-2344`), with the exception that [the section on the loader](#from-a-build-to-the-input) states.

## The language check

Before anything is compiled, the check reads each Lean file Lake would compile for the claim, and the project's Lake configuration, and refuses anything outside a closed set. If it admits the project, the gate builds and replays it and runs the rules on the result. A project whose Lake configuration has a `require`, or with Mathlib in its imports, can have only the proof verdict: the gate says so, builds nothing and exits with 3, and the operator gets that verdict with the three commands of [what a pass means](#what-a-pass-means) in the project, which run the project's code and its dependencies'.

The gate is `lake exe lint PROFILE full DIR`, from a checkout of Regula built apart from the project. Lake loads a project's configuration before anything Lake starts can run, and a `lakefile.lean` that runs can delete itself or plant a checker, so no run that the project's Lake started can give a full verdict. `Regula.Reader.startedOutside` refuses one: the checker's program must lie outside the project, and the Lake that started it must have dispatched from the checker's own package (`dispatchedFrom_iff`). This guards the start, and no more: a project's code that ran first can make any program print any line, so a verdict is worth what the start from outside gives it. [The confirmation record](confirmation.md#the-language-check) holds the restatement that the owner confirmed, the status of each consequence, and the second reading. The formal statement is `languageRecord` and `fullGateRecord` in [`RegulaSpecification/Language.lean`](RegulaSpecification/Language.lean).

**Every Lake call and child process of the gate works in a tree the checker made for this run**, a new directory from `IO.FS.createTempDir` that holds only the `lakefile.toml` and `lean-toolchain` it wrote and the text of each file it read, and that it removes afterwards. So no name, link or file of a project can select a path outside that tree, whatever Lake derives at this or a later version, and the verdict is about the text read. The project's directory is read by the checker alone, and is not written. Its `.lake`, its manifest and its other files are not read at all. A tree left by a crash can affect nothing later, because each run makes a new one. Three reviews of the earlier form, which ran Lake in the project's directory, each found another path that Lake derives from it, so the class is closed by leaving that directory.

### The closed set

The tables are data, in [`lean/Regula/LanguageSet.lean`](../lean/Regula/LanguageSet.lean). A construct is in them only if, read at the pinned Lean: Lean's toolchain declares its parser, its elaboration evaluates no code that the file writes or names, it changes no parser state a later command reads, and it installs no replacement for compiled code. That is the criterion each entry was read against, and H2 is what depends on it being read correctly. The set is what real library code uses and meets that criterion, so it is not every construct that meets it: anything else is refused, visibly, until someone reads it.

| Position | The table | Why it is closed |
| --- | --- | --- |
| A node's kind | `kinds` | Refuses each kind not read, including all that a later Lean adds. |
| A token | `atoms` | A token can sit in an optional position of an admitted kind, such as `meta section`. Refuses each not read. |
| An identifier | No component starting with `_`, other than a first `_root_`, and no `autoParam` | The compiler reads names of those forms by their form (`Lean/Compiler/LCNF/ToDecl.lean:25-27`), and `Lean/Elab/App.lean:832` evaluates what `autoParam` names. |
| `@[name]` | `simpleAttributes` | `Lean/KeyedDeclsAttribute.lean:166` and `Lean/Meta/Tactic/Simp/Simproc.lean:130` evaluate a named definition, and `implemented_by`, `extern` and `csimp` replace compiled code. |
| `set_option`, `leanOptions` | `options` | `debug.skipKernelTC`, `match.ignoreUnusedAlts` and `internal.parseQuotWithCurrentStage` change what is checked or parsed. |
| A tactic's `+item` | `configItems` | `+native` is a native proof. A `(config := ...)` is refused by its kind, because `Lean/Elab/Tactic/Config.lean:151` evaluates its value. |
| A `deriving` class | `derivingClasses` | A handler is code. |
| `namespace`, `open` | No start of the target may end a namespace that holds scoped parser entries in this file's environment | Keeps the parser's context constant: see H1. `open X (names)` activates nothing (`Lean/Elab/Open.lean:90`), so it needs no test. |
| The header | `module` is required, with the same tables for the rest, so `meta import`, `import all` and `prelude` are refused | In a `module` file with no `meta`, Lean itself refuses to evaluate a project's constant (`Lean/Compiler/IR/Meta.lean:56-59`, `Lean/Environment.lean:2537`), so a route that the table misses still meets Lean's check. |

The kinds of `leafKinds` hold open text, such as a string's or a comment's, and the check does not enter them. Thus `"run_cmd"` in a string or a doc comment is not a construct.

### H1 and H2

These are hypotheses about what Lean v4.35.0 does. They are stated in `LeanBehaviour`, never as axioms. No proof in Lean can reach them, because `Lean.Parser.parseCommand` is `partial` (`Lean/Parser/Module.lean:135`) and Lean's elaborator has no model here. The owner confirmed that a hypothesis of this kind, re-read at each upgrade of Lean, counts as Lean staying trusted. So "no bugs" here means no bug outside these stated, version-bound claims.

**H1: the tree the check read is the tree Lean elaborates.** The frontend calls the same `parseCommand`, with state from the elaborator (`Lean/Language/Lean.lean:595-601`). The parser reads that state only as scoped parser entries and tokens (`Lean/Parser/Extension.lean:607-612`, `Lean/Parser/Module.lean:124,146`), the option `internal.parseQuotWithCurrentStage` in quotations, and namespace and open declarations when it resolves a parser's name in a quotation (`Lean/Parser/Extension.lean:765`). Quotations and that option are refused. Scoped entries activate only at `open` and `namespace` (`Lean/Elab/Open.lean:83,89,101`, `Lean/Elab/BuiltinCommand.lean:60`), and no target of an admitted file can activate a namespace that holds any. No admitted command adds a parser, so the project's own modules add none to the environment. So the reader parses each file with one context: the environment of the toolchain's modules that the file sees, no options, no namespace and no open declaration. It computes what a file sees from `importModulesCore`'s rule for a `module` file (`Lean/Environment.lean:2108-2190`): each direct import, and through it each `public` import, in `Regula.Reader.visibleToolchain`. Lean's own function cannot do this, because it follows `.olean` files and the project's modules have none before the check admits them. **Proved**: `mem_visible_iff`, that the function gives what `Sees` states, with the bound it is given. That `Sees` is Lean's rule is the one place where the reader states what Lean does, and H1 covers it.

A simulation of the elaborator's state is what H1 avoids: Lean's parser and elaborator disagree on what `open ... hiding` activates (`Lean/Parser/Extension.lean:624-626`, `Lean/Elab/Open.lean:101`), so a restatement of that state would be a place for a bug to enter.

**H2: what the closed set admits runs no code the project wrote, and installs nothing that replaces what the compiler runs for a definition.** Each entry of the tables was read against the criterion above. **Assumed** from reading each evaluation site that a search of Lean's sources for `evalConst`, `evalConstCheck`, `evalExpr`, `evalTerm` and `evalDecl` finds, as of v4.35.0, and each of these is reached only through what the tables refuse: `Lean/Elab/BuiltinEvalCommand.lean`, `Lean/Elab/BuiltinNotation.lean:588,594`, `Lean/Elab/BuiltinTerm.lean:432`, `Lean/Elab/Tactic/BuiltinTactic.lean:683`, `Lean/Elab/Tactic/Guard.lean:163`, `Lean/Meta/Native.lean`, `Lean/Elab/Tactic/Config.lean:151`, `Lean/Elab/ConfigEval/`, `Lean/Elab/Tactic/Try.lean:1033`, `Lean/Elab/Util.lean:108`, `Lean/KeyedDeclsAttribute.lean:125,166`, `Lean/Meta/Tactic/Simp/Simproc.lean:130`, `Lean/Attributes.lean:450`, `Lean/Elab/DocString.lean`, `Lean/Linter/MissingDocs.lean:43`, `Lean/Linter/UnusedVariables.lean:143`, `Lean/Compiler/LCNF/Simp/ConstantFold.lean:648` and `Lean/Compiler/LCNF/PassManager.lean:217`. `Lean/Elab/Util.lean:108` is reached by Lean's own `autoParam` constants, which are the toolchain's code, and a project's is refused by the table and by Lean's check in a `module` file. A route in an admitted kind that this reading missed is a false pass, and that is what H2 stands for.

H1 and H2 say what a compile of admitted files runs. That nothing of the project runs before the check is no hypothesis about Lean: it is the start from outside and the reads by name above, measured below.

**At each upgrade of Lean:** `supportsLean` refuses any other release, so nothing passes until these are done. Diff the toolchain's kinds, and read what changed in each kind of the table. Run the search for evaluation sites again. Read again the sources that H1 cites, with `importModulesCore`, and the Lake sources that the reading table cites. Run the differential below.

### What remains

**Not closed, by design:** another process that changes the checker's tree. One that changes the project after the read cannot reach the verdict, which is about the text read. Anything about a dependency's code, since a project with a dependency has only the proof verdict. Lean, Lake and the kernel. A fake toolchain or a `PATH` shim: the check runs inside what it is given, and `supportsLean` reads only what that program says of itself. A checker that the operator did not build apart from the project. **Accepted risk:** a project that needs a file outside its Lean sources and Lake configuration during the build fails its full verdict, visibly, and one full verdict costs one fresh build. A project with a harmless dependency gets only the proof verdict, and a harmless name outside the closed domain is `incomplete`. A harmless link that a project's source is read through gets no full verdict, and neither does a library with a recursive glob over its own directory: each is visible, and the cost is to name the modules. A link in a file that no root and no import reaches is not read, so nothing selects it and it does not change the verdict. ### Decisions

Each of these was decided on the owner's behalf, and [the confirmation record](confirmation.md#the-language-check) gives the rest:

- One process runs the check, the build, the replay and the rules, because a record that a first command left could be forged by project code in the build that a later command read. So the order is a program's order, with a theorem.
- The table is what real code uses, not every construct that meets the criterion, because each entry is a claim that H2 rests on. Regula's core uses about 170 of its kinds, and the rest go with library code of two other projects of the owner's that is outside this repository.
- The specification package stays outside this check. It imports lean-intent, whose files use `syntax` and `macro`. So it gets the proof verdict, and its proofs are still replayed by `lake check`.
- The language decision reports each offending position and the shell prints at most 50, because a project far outside the set would otherwise print its whole tree.
- `Regula.Reader` and `Regula.Shell` are in the default target `RegulaChecker`, so a full verdict on Regula reads them, and every function of the checker that does not itself call Lake is in a default target too. They ask what calls Lake through the operations of `Regula.Effect`, and `Regula.Workspace` holds only those calls (`LakeCalls`). `Regula.LintMain` stays the thin `unsafe` root, because `Lean.enableInitializersExecution` requires it. `Regula.DiagnosticsGate` and `Regula.TestListing` are repository programs, not the checker.
- A library's or an executable's name must be in the closed domain, like a module's, because Lake joins an executable's name onto its output directory, and an absolute one selects a path outside the project. The root package's own name is not tested, because a default build uses it for no path. So a target named with a hyphen is `incomplete` until it is renamed, which is the cost of a closed domain.
- The configured paths are a closed domain: each source directory lies below the tree, and each `globs` entry is a single module, before any Lake call asks for the modules. A closed domain costs less than arguing about an open one. It refuses, as a configuration fault, and does not give `incomplete`, because the project's configuration states the path and nothing failed to read. `Reading.openPaths` holds each report, so a refusal with no reason is no state of the type.
- Every child of the gate works in a tree the checker made, and the checker reads the project by itself, on the owner's delegated agent's decision, because a list of the paths that Lake derives from a project's directory is the wrong shape, however complete it reads today, and a later Lake can add a row. The cost is one fresh build per full verdict, and a project that needs another file during its build fails. A project may keep its own `.lake`, since nothing reads it.

## Module files

Each Lean file of the root package is a `module` file. An importer that is a `module` file sees the type of a definition and the statement of a theorem, and it sees a body only where the author chose that: an `abbrev`, an instance or `@[expose]`. So what such a caller relies on is stated. **Measured** on 2026-10-31: Lean's header parser (`Lean.Parser.parseHeader`, `HeaderSyntax.isModule`) reported `module` for each of the 21 tracked Lean files below `lean/` at that date. The one added since, `Regula.ProgramCheck.EffectScan`, starts with `module` too, which the gate's build of it reads.

The root package has two `@[expose]`. One is on `Regula.ExecutableContract.run`: the exported theorem `ExecutableContract.run_eq` is proved by `rfl` over that body, and without the attribute it does not build. **Measured** on 2026-10-31. The other is on `Regula.Effect.Resp`: a caller gives a program of an operation the type of its response, which only that body shows. Its other visible bodies are the instances that `deriving` makes, the instance of `Monad` on `Prog`, and two `abbrev`: `Regula.Reader.Attempt`, so that `ExceptT`'s monad applies to it, and `Regula.Reader.ParserCache`.

`Regula.ProgramCheck.TestListing` proves two configurations equal by reduction, so it uses `import all` on the three modules whose unexposed bodies it reads: `Regula.TestListing`, `Lake.CLI.Main` and `Init.System.ST`. `Regula.ProgramCheck.Effects` states the bodies of `Regula.Workspace`, so it uses `import all` on that module. `Regula.TestListing` imports Lake a second time with `meta`, because `lean --run` runs it in the process that elaborates it, and only a module imported with `meta` has its runtime initializers run there (`Lean/Compiler/InitAttr.lean:160-168`). **Measured** on 2026-10-31: without `meta`, the process ended with signal 11.

In this package, only `RegulaSpecification.Input` is a `module` file. **The remaining files, but for `Proofs.Gate`, cannot be one yet.** A `module` file cannot import a file that is not one (`Lean/Environment.lean:2120`), and no file of lean-intent at the commit that `lakefile.toml` names is one. **Measured** on 2026-10-31 with the same parser, over its tracked files. `RegulaSpecification.RuleRecord`, `RegulaSpecification.Language` and `RegulaSpecification.Effects` each import three of lean-intent's modules, and each other file but `Proofs.Gate` imports one of the three directly or through another of them. It is not a `module` file either, and it unfolds that module's unexposed bodies, which a `module` file would see only through `import all`.

A file that is not a `module` file sees each body of what it imports, whatever the author chose (`Lean/Elab/Import.lean:150-156`, `Lean/Environment.lean:2183`). So the proofs read the executed definitions of `Regula.Rules` as they did before, with no `import all`.

## Decisions of this specification

Each of these was decided on the owner's behalf by the owner's delegated agents, because the owner's intent asks for the smallest core that does the job. None is the owner's confirmation.

- The root package does not set Lake's `requiresModuleSystem`. Lake would then warn on each file that is not a `module` file and imports one (`Lake/Build/Module.lean:416-424`), so the proofs here and another project that imports `Regula.Contract` would need `allowNonModules`, and a file that imports nothing of the package would still not be seen. A `module` file that imports a file that is not one is already refused by Lean, and a file that stops being a `module` file is cheap to correct.
- The root package does not set `allowImportAll`, because no other package's file uses `import all` on one of its modules at this revision.
- The specification's files are not split so that the parts without a lean-intent record could become `module` files now. No importer of those parts is a `module` file, so a split would move each statement and show nothing more, and the whole package can migrate at once.
- The claim is the default targets of the root package, with each module of the root package that their imports reach. That is the set `lake check` replays, so a project cannot claim a target that `lake check` skips, and it needs no file of its own that classifies its targets. A target that is not a default target and that no default target imports is outside the claim, as it is for `lake build` and `lake check`. **Measured**: such a module with a `sorry` passes, and it fails once a default module imports it.
- A project states one profile, for all of its claimed modules, and no profile is `incomplete`. A library that needs a stricter profile than another is a project of its own.
- The input is one environment, because `lake check` already needs one, and it holds each constant of that environment, so the loader has no search of its own and no loop. To check a constant that the import replaced, it reads the rules' `Tables.axiomSet`.
- A rule reads only an input of the closed form, by its type. The checker's type holds what the rules read of it, and `Draft.admit` is the one place that decides the two parts that a real build can lack: a claim of no module and a mention of a constant that the input does not hold. What the loader constructs is carried instead of checked: unique names, and that a claimed module is loaded. So the two checks of those and the field `loads` are gone, and their theorems `not_wf_duplicated` and `unloaded_refused` with them. The record of the verdict still states what the admission refuses. The rule's record reads a well-formed input by its type, so `SameReports` says nothing of the others, and each rule still has its two witnesses.
- The rules read `Tables i`, whose proof fields state what each table holds of `i`, rather than a table with no relation to the input, so `rgN_exact` holds of every value of that type.
- `Safety` replaces the flags `isUnsafe` and `isPartial` of a constant, so the form of a recursion helper does not exclude a state that Lean does not make. `safetyOf` reads Lean's two flags, and the theorems state what it gives in their terms.
- `Report` replaces the triple of a verdict, its findings and an optional reason, so the printer has no default for a reason that is missing.
- A lookup with `getD _ []` stays in `Input.mentionedBy`, `Input.axiomReach`, `Facts.stated` and `Facts.input`. Each table is a map from a name to a list of what it relates, where a missing key and an empty list are one state, so the default stands for no excluded state.

A set follows what every loaded module's own data states, so on a build where Lean's import replaced a constant it can hold more than `Lean.collectAxioms` gives on the merged environment. **Measured** once on 2026-10-31 by `lake lint`, against pull request 515: on the root package 5.1 s real and 4.7 s user, against 4.2 s and 11.4 s, with a largest resident set of 0.74 GiB against 0.74 GiB; on this package 5.2 s and 4.8 s, against 4.6 s and 19.2 s, with 0.75 GiB against 0.69 GiB. ## The run of the checker

The checker's whole run is a value of the type `Regula.Effect.Prog`, `Regula.Shell.run`: a tree whose every node names one operation of the closed type `Op`, with what to do for each response that operation can give. The tree performs nothing. `Prog.interpret` runs it, in `BaseIO`, through one table, `Regula.Effect.table`. An operation that can fail gives its failure as a value of its response, so `BaseIO`, whose type holds no exception, leaves the tree one way out: its leaf.

`Runs p t a` says that for the responses that the events `t` hold, `p` asks exactly the operations of `t`, in that order, and ends with `a`. A response is any value of its type, so a statement over `Runs` holds for every answer of Lean, Lake and the operating system, a failure included. It is a fact about what the run received and what it did with it, so no theorem rests on the file system staying still: another process can change any file between any two reads and back, and the statement holds of what the run read.

**Proved** of the definition that the executable runs, in [`RegulaSpecification/Proofs/`](RegulaSpecification/Proofs/), with the statement in [`Effects.lean`](RegulaSpecification/Effects.lean), [`EffectsRun.lean`](RegulaSpecification/EffectsRun.lean) and [`EffectsRecord.lean`](RegulaSpecification/EffectsRecord.lean). The original statements preceded the program; the preparation relations strengthen the record against the unchanged reader and shell. `run_meets`, for every argument list and every response (`RunMeets`):

- **Refusal.** A Lean other than the pinned one, or arguments of neither form, or a text that is no profile: exit 2, the last line of an incomplete proof verdict, and the run only says so (`Refusal`).
- **The proof verdict.** The exit code and the last line are those of `Regula.Closed.decision` on what the load gave, and the load gave what the proved `Facts.input` gives on the environment, the places and the modules that Lean and Lake returned, or an error for a case of `PlainReason`, each of which is what a response said about an operation that this load needs (`PlainRun`, `Loaded`, `BuildRead`). `PlainPreparation` directs the workspace load by earlier responses and requires its root's `leanPath` before every lookup or rules import, without another setter between. It requests no tree mutation. Exit 0 gives `EnvForm` and `EnvFloor` of what they returned (`plain_exit_zero`), and that no answer failed.
- **The check.** Its outcome is that of `Regula.Language.decision` on the reading. An admitted reading rests on `Evidence`: the real path of the project and the tree, which lie apart; the start from outside; `lean-toolchain`; `lakefile.lean` absent by its name; each key path of `lakefile.toml`, whose text is the text in the tree; and for each file (`ReadAs`), that it passed the exact-path test, that the text that `readFile` returned is the text written to the same relative path of the tree, and that Lean's parser gave its header and commands from that text in the environment of exactly the toolchain modules that `Sees` states. Any other outcome rests on a `Reason`, a closed set of what the responses said about what the requested build needs, by what the run has been told of that build (`Scene`, `Named`, `Needed`): a read of anything else justifies nothing. So a reader that refuses without one does not meet the record. On an admission, no read failed (`readProject_no_failed`).
- **Nothing is built unless the check admitted.** The events of the check hold no Lake command and no load for the rules (`only_readProject`). On any other outcome the gate asks nothing more.
- **Writes.** Each act of a full run, each `writeFile`, `createDirAll`, `removeDirAll` and the working directory of each Lake command, lies at or below the tree or is the tree, and the project's real path and the tree's lie apart, so a run writes nothing to the project's directory (`Confined`). Every write asks `Regula.Reader.inTree` first.
- **Preparation at each occurrence.** `ReadingPreparation` fixes the complete acts of the reading: the TOML copy from an earlier source read, the pinned `leanToolchain` copy, the configuration load, and module copies after setting that load's `root.toolchain`. Each `CopyStep` creates only its path's parent, when present, and writes only after that succeeds. A failed directory ends the step; a failed configuration copy ends the acts, while a failed module copy permits later module steps. A path or parent outside the tree makes no act. Every module step has `Named`, `FileOfModule` and `SourceText` from its preceding prefix; repeated names or paths need that provenance again. Every parser import or lookup follows the setter, with no replacement setter. `readProject_preparation`, `inputOf_preparation`, `loadTree_preparation` and `loadPlain_preparation` prove the relations on the actual definitions' exact traces and compose into `run_meets`, so legitimate failures remain admitted.
- **Build and reload.** `BuildProtocol` permits exactly one build and, only after it succeeds, one replay, using the identified Lake in the allocated tree. Only reporting can occur between these operations. `BuildAndRules.no_mutation` excludes explicit writes, directory creation, allocation and removal from both the build and reload phases. `RulesPreparation` directs the reload by the received real path and puts the loaded root's `leanPath` before every rules import or lookup, with no later setter. `buildAndReplay_protocol`, `rules_reload` and `loadTree_preparation` prove these constraints for the actual definitions on every response; none describes filesystem effects inside trusted Lean/Lake calls.
- **Removal.** On every way out of a run that made its tree, the run asks `removeDirAll` of it (`FullRun`). `FullRun.removal_order` places the sole removal after reading, building and reloading, followed only by reporting; `FullRun.no_remove_before_command` excludes removal before any later Lake command. If the initial allocation fails, it is the first event and only reporting follows. A failed removal changes no verdict.
- **Exit code and last line.** Each is a function of the verdict alone, `Regula.Language.Report.exitCode` and `label`, or `Regula.Closed.Verdict.exitCode` and `proofLine`. The last event requests one physical verdict line, and every physical line requested by preceding `println` calls starts with two spaces (`EndsWith`, `IsDetail`). `detailText_no_break` proves that diagnostic serialization escapes LF and CR for every string; `serialized_split` relates those physical lines to the concatenated characters, including each LF that `IO.println` appends, and `endsWith_serialized` gives their final-line distinction. These statements concern the checker's requested output: output from Lake's child processes, partial writes and external writers are not `println` events of this trace. A failed print changes nothing the run decides. Exit 0 from the full gate gives all of the above with both Lake commands ending with 0 and the floor of the build (`full_exit_zero`).

**Not vacuous.** A program that does nothing fails the record (`constant_program_fails`), and so does one that reads nothing and refuses everything (`refuser_fails`). `admits_a_project` is conditional: for paths that meet the hypotheses `WitnessPaths`, it gives responses on which the check that runs admits a project. [A pass is owed](#a-pass-is-owed) states the rest. The hypotheses are what the tests of a path give, because `System.FilePath` depends on `System.Platform.isWindows`, an `opaque` constant (`Init/System/Platform.lean:22`, `:39`) that no reduction of the kernel can evaluate; that the pinned text trimmed is itself, on which `decide +kernel` got stuck (**measured**); and that an empty log holds no error, which is read from `Lean/Message.lean:702-703` and assumed. No theorem discharges them. **Observed**: the gate's run on Regula's own checkout takes the same branches on real paths and ends with `full verdict: pass`.

**The link to the executable.** `interpret_runs` and `executed_meets`, for any table and from any state of the world: what `Prog.interpret` computes is the value of a run whose events are what the program asks, each with the table's answer at the world the run has reached. `BaseIO` is a state monad in Lean's own definition (`Init/System/ST.lean`), so this is a theorem about that definition, and no assumption that effects run in program order. That the compiler keeps that order stays with the compiler.

### A pass is owed

The record requires both relevance and preparation. A reason names something the requested build needs; the exact phase relations constrain every operation whose response depends on the tree or search path that the run sets, including failed attempts. The earlier gap arose because membership in a trace established relevance while permitting inserted acts that could spoil a later operation. Ordered segments now close that gap in the record itself, independently of the owed-pass premises. The following results hold for every program meeting the record, in [`Proofs/Preparation.lean`](RegulaSpecification/Proofs/Preparation.lean), [`Proofs/Owed.lean`](RegulaSpecification/Proofs/Owed.lean) and [`Proofs/OwedExact.lean`](RegulaSpecification/Proofs/OwedExact.lean):

- **A non-pass has a defined reason.** `Reason`, `Needed`, `PlainReason`, `TreeReason` and `BuildRejected` are closed. Each case binds its event to the requested build through what the run was told: the answer to `LEAN_SYSROOT`, the real path of the project and of the tree, Lake's load of that tree, the modules of its default targets, a name the build needs (`Named`, each module of a default target and what the file of such a name imports), and that name's file. **Proved**: `manufacturer_fails` excludes the program that reads an unrelated environment variable and reports incomplete; `misjudge_fails` excludes the program that receives a successful `LEAN_SYSROOT` response and reports incomplete without loading; `unrelated_read_no_reason` excludes a failed read of a path the build does not name. Preparation comes from the same run's phase relations, so none of these relevance predicates alone is the whole contract.
- **Copies cannot manufacture their own preparation.** `ReadingPreparation.first_directory` states that when the first tree act creates a directory, that directory is the TOML destination's parent. `manufacturedCopy_fails` excludes the reported trace that reads the TOML, creates a directory at its destination, fails its write, removes the tree and reports incomplete, for every path, text, error, profile and exit code. Its proof uses the missing toolchain response; the separate first-act theorem gives the directory-order property. Each later step needs a named module's file and an earlier source read; a child path that obstructs another named file is therefore a conflict directed by the project's own configuration. `BuildAndRules.no_mutation` and `FullRun.after_removal_saying` exclude later explicit writes and nonterminal removal. No theorem infers filesystem contents from arbitrary response values.
- **A pass is owed under the defined premises.** `PlainOwed` excludes `PlainReason` and requires the floor of each loaded reading. `FullOwed` excludes allocation failure, admission reasons, build/replay rejection and reload reasons, and requires the loaded readings' `LoadFloor`. **Proved**: `plain_owed`, `full_owed`, and `run_plain_owed`, `run_full_owed` at the whole run give the pass verdict and exit 0 under these premises. `pass_iff_floor` states the pure part in terms of the environment alone: the loader and the rules pass exactly on `LoadFloor`. Preparation follows from `PlainRun` and `FullRun` even when these owed-pass premises do not hold.
- **Exactly then.** `plain_exit_zero_owed` and `full_exit_zero_owed` state the other direction, and `run_plain_exit_zero_iff` and `run_full_exit_zero_iff` state both of the program that runs. That direction has a hypothesis, decided on the owner's behalf: `OneAnswer`, each operation asked twice got one answer, on the phases that `readPhase` and `rulesPhase` give, and `OneContext`, one parser context for one input. Without it a run can pass on what it judged while another answer to the same operation would be a reason, as when another process changes a file between two reads of it. Such a pass still rests on what it read (`full_exit_zero`). `oneAnswer_traceWith` states that answers given by a function of the operation meet `OneAnswer`.

### So thin that it only calls Lean

The owner's words say "so thin that it only calls Lean". The owner's delegated agent stated the form on the owner's behalf, because a form that a reader could not check would let a decision back in: **a definition has this form when it only calls Lean or Lake, as a straight line of calls that passes each result on, with no test or branch of its own on any result.** Turning a failure into the `Except` of a response (`toBaseIO`) is no decision. These stay assumed. Each is a statement about a system or a step that no proof of Regula examines.

- Lean's kernel, elaborator and runtime, and Lake's load and build. The owner trusts Lean and its kernel.

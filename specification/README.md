# Specification of Regula

[`README.md`](../README.md#purpose-and-constraint) states Regula's purpose and the owner's constraint on all work. [The trusted base](#the-trusted-base) states what this revision rests on, and [the run of the checker](#the-run-of-the-checker) what is proved of its effects.

This document states what Regula's checks are, what each is proved to do, and what stays assumed. It follows the order that the owner chose: first a small proved core, then [a check](#the-language-check) that reads each source file before anything is compiled and refuses anything outside a closed set of allowed constructs. [The confirmation record](confirmation.md) holds the owner's words.

## How to read this document

Each claim about Lean, Lake or the theorems of this package has one of four marks:

- **Proved**: Lean checks a theorem of the Lean package in this directory. The theorem name follows the mark.
- **Measured**: an observation on the pinned toolchain, with its procedure.
- **Assumed**: a behaviour of Lean, Lake or the operating system that a verdict relies on and that no proof here examines. Each is an entry of [the list of assumptions](#the-trusted-base), and its name follows the mark, as in **Assumed** (`files`).
- **Open**: an obligation that this document does not discharge.

A statement about Lean's or Lake's source that explains a design, and that no verdict relies on, says that it is read from the source, with its lines.

A statement of what a rule or the checker must do is specification, and it has no mark. A citation such as `Lean/Meta/Native.lean:45` is a path below `src/` of the tag `v4.36.0` of Lean, the toolchain that `lean-toolchain` pins, and one that starts with `Lake/` is a path below `src/lake/` of that tag. To check all statements and theorems, run `lake build --wfail` in this directory. The Lean library `RegulaSpecification` requires lean-intent at the commit that `lakefile.toml` names, and the root package.

## The shape of a rule

Each rule is a pure function from the closed input to the subjects that it reports, and a pair of modules. Its check is `Regula.Rules.RGnnnn` below [`lean/Regula/Rules/`](../lean/Regula/Rules/), a value of `Regula.Closed.Rule` whose one import of the checker's modules is its core, `Regula.Rule`, with every table that the rule alone reads. Its statement and proofs are `RegulaSpecification.Rules.RGnnnn` below [`RegulaSpecification/Rules/`](RegulaSpecification/Rules/), which imports of the two packages only this package's core, `RegulaSpecification.Rule`, the rule's own check and, with `import all`, that check again and the checker's core, whose bodies its proofs unfold ([Module files](#module-files)). No rule's module imports another rule's. The checker's registry, `Regula.Closed.registry` in [`lean/Regula/Rules.lean`](../lean/Regula/Rules.lean), lists the rules that a run applies, in the order of their findings, and stamps each finding with its rule's spelling. This package's registry, `registry` in [`RegulaSpecification/Rules.lean`](RegulaSpecification/Rules.lean), lists each rule as a value of `Proved`: the rule that the checker runs, its violation predicate, the proof that its check reports exactly the violations, its cases, and the proof of the kind of subject that its violations carry. `registry_rules` proves the two lists one, by `rfl`, so a rule that one registry holds and the other does not stops the build. [`CONTRIBUTING.md`](../CONTRIBUTING.md#adding-a-rule) gives the procedure for adding a rule.

**Measured** on 2026-11-03, with Lake's own output on an incremental build of both packages that were up to date at the change's commit, one edit at a time, each restored before the next. A one-line edit of `Regula.Rules.RG1003.check`, its finding's text, rebuilt in the checker's package only that module, its object file and the `lint` executable: the registry and the shell were not rebuilt, because a `module` file's importer sees the check's type and not its unexposed body, and Lake traces an import of a `module` file by its public `.olean` (`Lake/Build/Module.lean:363-368` and `:567-570` at v4.36.0). This package's files were not `module` files then, so Lake traced their imports by every artifact of each module they reached (`Lake/Build/Module.lean:347-350`): that edit rebuilt 31 modules here, RG1003's own and the 30 that imported it, directly or not, and a one-line edit of `rg1003_exact`'s proof that changes its proof term rebuilt nothing in the checker's package and 26 modules here. **Measured** again on 2026-11-17, with each file of this package a `module` file, by `lake build` in this directory with both packages up to date, one edit at a time, each restored and rebuilt before the next. The same edit of the check rebuilt `Regula.Rules.RG1003` and, of this package, only `RegulaSpecification.Rules.RG1003`, which reads the check's body through `import all` (`Lake/Build/Module.lean:352-355`). A `have` added to the proof of `rg1003_exact` rebuilt only `RegulaSpecification.Rules.RG1003`. Neither edit rebuilt another rule's module. An edit that changes what a module of this package exports, such as the body of one of its definitions, was not measured. The gate builds both packages from clean and does not use this: on 2026-11-03 the owner decided to keep it so, since reuse would then have saved about 14 s of its 146 s on a one-rule change ([the record](confirmation.md#2026-11-03-the-local-gate)). What reuse would save with this package's files as `module` files was not measured.

Its formal statement is a lean-intent intent record (`LeanIntent.IntentRecord`), built by `ruleRecord` in [`RegulaSpecification/RuleRecord.lean`](RegulaSpecification/RuleRecord.lean). The record has one property: on each well-formed input, the function reports a subject exactly when the subject violates the rule. Thus the meaning of a rule is all in its violation predicate, for example `Violates1005`.

For each rule, the package gives a case that the rule must refuse and a case that it must admit (`Witnessed`). From them, it proves that the record meets lean-intent's obligations O2 (at confirmation and before a run), O3, O4, and O5 with the freedom `SameReports`, which is the order and the repetition of the reported subjects. A rule's function takes the proof of the closed form with its input (`Checker`), so the record has no case for an input that the admission refuses. **Proved**: `adequate`, applied in `rg1001_adequate` and the theorems that follow it. O1 holds for each record. **Proved** by lean-intent: `LeanIntent.o1_wellTyped`.

Each rule function that the checker runs is proved against its record in its own module below [`RegulaSpecification/Rules/`](RegulaSpecification/Rules/) (`rgN_exact`, `rgN_meets`, `rgN_cases`). The functions run over `Regula.Closed.Input`, so the proofs are about the executed definitions, not about a copy of them.

These theorems have no hypothesis about the input or about the tables that a rule reads, because the types carry them. A value of `Regula.Closed.Input` has the closed form (**proved**: `wf_toSpec`), and a value of `Regula.Closed.Tables i` holds what each table holds of the input `i`, so `rgN_exact` holds of every value of that type. A rule computes an axiom set from the input itself, by a search backwards from each axiom through the constants that each constant mentions (`Tables.axiomSet`), and that set is exactly what `Input.AxiomOf` states (**proved**: `Tables.mem_axiomSet`, `axiomSet_iff`, with `mem_reach`). The checker does not call `Lean.collectAxioms`, so nothing about that function is assumed.

## The closed input

The closed input is the type `Input` in [`RegulaSpecification/Input.lean`](RegulaSpecification/Input.lean):

| Field | Owner and interface |
| --- | --- |
| `profile`, the profile that the project states | The one argument of the lint driver, `lintDriverArgs` of the project's Lake configuration |
| `modules`, the claimed modules | Lake's load gives the modules of the default targets of the root package; each loaded module whose `.olean` lies in the root package's library directory is claimed |
| `moduleFiles`, the loaded modules that are `module` files | The flag `isModule` of each loaded module's data in the environment's header, which Lean writes into the `.olean` from the header of the environment that elaborated the file |
| `decls`, each constant of the environment | `Lean.importModules` with `loadExts := false`, at the level `.private` |
| `claimedConstants`, of the names that the entries of `csimps` give, each one declared in any claimed module's own `.olean` data | `Facts.claimedCSimpTargets`: returns `[]` immediately when `csimps` is empty; when `csimps` is nonempty, indexes only the target names of `csimps` and scans `Facts.claimedConstants` once for hits, returning each owned target name once, leaving `Facts.stated` unchanged and reading no dependency module's constants (`Facts.claimedConstants` steps once over the loaded modules, dependencies included, to select the claimed ones), so claimed-module ownership comes strictly from claimed `moduleData` rather than `const2ModIdx` |
| `csimps`, each exported (`global` or `scoped`) `@[csimp]` entry registered in a claimed module | `Lean.Compiler.CSimp.ext.ext.getModuleEntries` at each claimed module's `getModuleIdx?`, under `loadExts := false` at `.private` |
| `unique`, that no name is that of two constants | The loader's proof, from the keys of the hash map that holds the constants (`Std.HashMap.distinct_keys_toList`) |

The input has no source text, message, compiled code, option or build log. A rule does not decide what it cannot read in this input.

The admission refuses an input that does not have the closed form (`Input.WellFormed`). Each constant that a constant mentions is held (**proved**: `open_mention_refused`). At least one module is claimed, so a claim of nothing is not read as a pass (**proved**: `no_claim_refused`). **Proved**: `admit_ok_iff` for the function that the checker runs, `Draft.admit`, which gives the proofs of both to the type that the rules read.

What the type excludes needs no check. The type `Input` of this package cannot hold a name twice, as an environment keeps its constants in a hash map, and the checker's `Facts` carries that its modules are those of the environment's header, so a claimed module is a loaded one (**proved**: `claimed_loaded`). `Safety` cannot state a constant that is both unsafe and partial, which Lean does not make (**proved**: `not_unsafe_of_partial`). `Regula.Closed.Report` cannot state a pass with a finding, a failure with none, or an incomplete run with no reason.

The shell has four effects on the plain `lake lint` path: it loads the build, it replays the cone of the build's claim, it prints its report, and it sets its exit code. It writes no file there. It runs no initializer of the loaded modules, because it loads them without extension states. Lake's own load of the workspace on that path runs Git in the environment of the caller. The full gate takes another path: it loads the root package's configuration alone, which resolves no dependency, and has more effects, which [the language check](#the-language-check) gives: it reads source files and, once it has admitted them, writes them to a tree of its own, which it removes afterwards, it imports the toolchain's modules with their initializers to parse those files, and for an admitted project it runs `lake build --wfail` in that tree and replays the cone of the build's claim. [The run of the checker](#the-run-of-the-checker) states these effects.

## From a build to the input

`Regula.Load.Facts.input` is the pure function that fills the input from an environment, and [`RegulaSpecification/Proofs/Load.lean`](RegulaSpecification/Proofs/Load.lean) states what it gives. So a later change to the loader that drops a constant, a field or a mention fails the gate's build of this package.

- **Proved**: `pass_iff`. For every environment, every `Facts` and every profile, when the loader gives an input, the checker passes on it exactly when the environment has `EnvForm` and `EnvFloor`. These two statements name no field of the input. `EnvForm` is the closed form. `EnvFloor` states RG1013 of each claimed module, by the data that the header holds of it (`EnvModuleFile`), RG1011's `@[csimp]` condition of each claimed module (`ModuleCSimpIn`: each exported `@[csimp]` entry registered in a claimed module names a constant declared in some claimed module's own `moduleData`), and RG1001 to RG1006, RG1011 and RG1012 of each constant of `Environment.constants.map₁` in a claimed module. What a name mentions, and whether it names an axiom, is read from the fields of the `ConstantInfo` that `map₁` keeps and of each constant of that name that a loaded module's own data states (`EnvMentions`, `EnvAxiom`, `mem_usesIn`, `mem_stated`).
- **Proved**: `pass_floor`, the same of `Regula.Closed.decision` on what `Facts.input` gives. The shell runs kernel replay after `Regula.Load.Facts.prepare` (`Regula.Shell.inputOf`, `replayed_spec`) and evaluates `Regula.Closed.decisionPrepared` on that final load result; `decisionPrepared_eq` and `Facts.prepare_tables` prove that report equal to `Regula.Closed.decision` on the corresponding input-or-error result. A pass also states that each module of a default target is claimed, that each claimed module is loaded, and that each constant of the environment has a module. `input_form` states the closed form of each environment that the loader gives an input for.
- **Proved**: `pass_held`. On a pass, each constant of a claimed module, as that module's own `.olean` states it and also when Lean's import replaced it (below), has either neither replacement attribute in that module's own entries (`ModuleUnreplaced`) or only `@[implemented_by ind.ctorIdx._impl]` for a verified `ctorIdx` definition (`ModuleCtorIdxEntryOnly`), has, when it is a definition, no initialization function in them (`ModuleUninitialized`), is no axiom, is either partial and not unsafe (a recursion helper) or unsafe with verified `ctorIdxShape f.env n info = .impl ind` (`T.ctorIdx._impl`) when it has either flag or a recursion helper's name, has no value that mentions a loop construct, has, when it is a definition or an opaque constant, no value that mentions `Lean.Order.fix` and no value that mentions a panic form (`EnvPanic`), and reaches through what it mentions only axioms that the profile admits. That theorem does not state the rest of the helper's form of such a constant; `pass_iff` states it of the constant that `map₁` keeps.
- **Proved**: `decision_pass`, `decision_failed`, `profileOfRun_ok` and `profileOf_eq_some`, for the shell's pure decisions. `mem_claimed_place`, `toolchain_place` and `below_iff`, for what the places of the modules decide, and `moduleOf?_eq` for the module of a constant. `startsSearchPath_eq_true_iff`, in both directions, for the workspace search-path comparison.

**The constants that Lean's import replaces.** Lean refuses two imported modules that declare one name with different values, with one exception. It merges two theorems of one name and type, a theorem with an axiom of that name and type, and two such axioms, and it keeps one constant under the name of the first module that holds it (`subsumesInfo` and `finalizeImport`, `Lean/Environment.lean:2633` and `2700-2709`). So the loader reads the own constants of every loaded module from the header of the environment, claimed or not (`Facts.stated`), and what any of them mentions, and whether it is an axiom, counts for its name. On a pass, each axiom reached from a constant of a claimed module, by following mentions that any loaded module's own data states, is one that the profile admits (**proved**: `pass_floor`, `pass_held`, `mem_stated`). So a replaced dependency theorem's mentions now count, and so does a dependency's axiom that a theorem replaced, and this can refuse a build whose merged environment is clean. A constant of a claimed module that the environment does not show to the rules must also be a theorem, with neither flag and no recursion helper's name (`fitsUnshown`), whose value mentions no loop construct, and whose mentions reach only axioms that the profile admits, or the run is `incomplete` (`Facts.claimedConstants`, `Facts.unread?`). **Measured** on 2026-10-31 on this change, before it took in pull requests 516 and 518, on disposable projects, each after `lake build --wfail`: the project above gives `incomplete` or `fail` by the order of its imports, and passes under `standard-logical`. Under `kernel-only`, a module that mentions a dependency's theorem `bridge` whose proof uses `Classical.choice`, beside a claimed module whose `bridge` uses no axiom, gives `fail` (RG1005). With a theorem `shared` that mentions `bridge` and that the second module also replaces, it gives `incomplete`, and it passes under `standard-logical`. A module that mentions a dependency's axiom `x`, beside a claimed module with a theorem `x`, gives `fail` (RG1003, RG1005) under `kernel-only` and under `standard-logical`. When the dependency's `bridge` uses no axiom, the `kernel-only` project passes, and so do the two modules with `f.eq_def` under `standard-logical`.

## The rules

### RG1001 to RG1005: the foundation profile

Each reads a constant of a claimed module. RG1002 to RG1005 read its transitive axiom set `Input.AxiomOf`, which the rules compute from the input (`axiomSet_iff`). The four refine one refusal: each axiom that RG1002, RG1003 or RG1004 names also violates RG1005 for each profile. Thus a wrong choice between these rules changes the rule of a finding, but not the verdict. **Proved**: `rg1005_of_hole`, `rg1005_of_unknown` and `rg1005_of_compiler`. The formal statements are in one module for each rule below [`RegulaSpecification/Rules/`](RegulaSpecification/Rules/), with the vocabulary that more than one of them reads in [`RegulaSpecification/Foundation.lean`](RegulaSpecification/Foundation.lean) and the three theorems of the refinement in [`RegulaSpecification/Refinement.lean`](RegulaSpecification/Refinement.lean).

- **RG1001: project axioms.** A constant of a claimed module has the kind `axiom`. An assumption is a hypothesis or a field of a structure, so that each theorem that uses it shows it in its type. `lake check` refuses an axiom only when a constant mentions it, so it does not do the work of this rule. `Violates1001`.
- **RG1002: proof holes.** A constant depends on `sorryAx`, directly or through an import. `Violates1002`.
- **RG1003: unknown axioms.** A constant depends on an axiom other than `propext`, `Quot.sound` and `Classical.choice` of the toolchain, and RG1002 and RG1004 do not name it. `Violates1003`, with `Input.Known`. **Assumed** (`leanImport`): Lean finds the library of the toolchain only below the `lib/lean` directory of the pinned toolchain, which the shell reads to say that a module is in that library.
- **RG1004: native proofs.** A constant depends on an axiom with the name form `<declaration>._native.<tactic>.<suffix>` that `native_decide`, `decide +native` and `bv_decide` add (`Lean/Meta/Native.lean:45` and `75-82`), or on an axiom by which the kernel trusts the compiler, of which `v4.36.0` declares none. `Violates1004`, with `NativeProofAxiom` and `compilerAxioms`. **Measured**: `native_decide` gave `n._native.native_decide.ax_1_1`. The rule identifies the axiom by its name, so an author can give an axiom that name. Then RG1004 reports it in place of RG1003, and the verdict is the same.
- **RG1005: the profile.** A constant depends on an axiom that the project's profile does not admit. Kernel-only admits no axiom. Choice-free admits `propext` and `Quot.sound`. Standard-logical also admits `Classical.choice`. Each admitted axiom is the toolchain's own. `Violates1005`, with `Input.Admits`.

### RG1006: `unsafe` and `partial` declarations

The rule refuses four things in a claimed module: an `unsafe` or `partial` constant without an exempted form, a constant with a helper's name without an exempted form, a constant whose value directly mentions a loop construct of Lean, and a definition or opaque constant whose value directly mentions `Lean.Order.fix`. `Violates1006`, with `Input.HelperForm`, `Input.CtorIdxImpl`, `HelperNamed`, `MentionsLoop` and `MentionsOrderFix`, in [`RegulaSpecification/Rules/RG1006.lean`](RegulaSpecification/Rules/RG1006.lean). **Proved**: `rg1006_exact` in both directions, `rg1006_checker_refuses_loop` for each construct, `rg1006_checker_refuses_forged_name` for a plain definition with a helper's name, `rg1006_checker_refuses_partial_fixpoint` for a definition and an opaque constant whose value mentions `Lean.Order.fix`, `rg1006_checker_admits_fix_theorem_and_lfp` for a theorem mentioning `Lean.Order.fix`, a definition mentioning `Lean.Order.lfp_monotone`, and a definition mentioning `Lean.Order.fix` only in its type, and `rg1006_admits_ctorIdx`, `rg1006_refuses_forged_ctorIdx`, `rg1006_admits_ctorIdxImpl` and `rg1006_checker_ctorIdx` for the compiler-generated `ctorIdx` exemption. The fourth clause was added in `v0.14.0`, and the `ctorIdx` exemption in `v0.15.0` for Lean `v4.36.0` ([2026-11-20](confirmation.md#2026-11-20-lean-v4360-and-compiler-generated-ctoridx)). In the terms of the environment, a pass gives that no claimed definition or opaque constant directly mentions `Lean.Order.fix` in its value (**proved**: `pass_iff`, through `EnvFloor`, `pass_held`, and `pass_occurs` under `UsedConstantsComplete`).

**The loop constructs.** The class comes from Lean's `Init/While.lean`. A `while`, `repeat` or `repeat ... until` needs no `partial` of the module that uses it, because it compiles through `Lean.Loop.forIn` to `repeatM`, whose body is a private `partial` of that file. So the flags alone do not show a loop that does not end. The rule reads the value of each claimed constant for the one value of the type `Lean.Loop`, `Lean.Loop.mk`, and for `repeatM` (`loopConstructs`). `termination_by` and `for` over a list stay allowed; computational `partial_fixpoint` definitions are now refused by the `Lean.Order.fix` clause below ([2026-11-20](confirmation.md#2026-11-20-partial_fixpoint-under-rg1006)). The owner's delegated agent added the loop clause on 2026-10-31, after `while true` passed all three commands while a `partial def` of the same loop failed.

**Measured** on 2026-10-31 (before the 2026-11-20 `Lean.Order.fix` clause) on a disposable project: `while`, `repeat`, `repeat ... until`, a direct `repeatM`, a direct `Lean.Loop.forIn ⟨⟩`, `forIn Lean.Loop.mk` and an `Inhabited Lean.Loop` instance were each refused; `termination_by`, `partial_fixpoint` and `for` over a list passed.

**Partial fixpoints (`Lean.Order.fix`).** Read from Lean `v4.36.0`'s source, and relied on by no verdict: `Lean.Elab.partialFixpoint` (`Lean/Elab/PreDefinition/PartialFixpoint/Main.lean:76-226`) handles `partial_fixpoint`, `inductive_fixpoint` and `coinductive_fixpoint`. For `partial_fixpoint` (`:103-111`), Lean synthesizes a `CCPO` instance or, when none exists (for example on `Nat → Nat`), synthesizes an inhabitant and falls back to `FlatOrder.instCCPO` (`Init/Internal/Order/Basic.lean:964`); `mkFixOfMonFun` (`:192`, `Lean/Meta/Order.lean:52-58`) constructs the packed value with `Lean.Order.fix` (`Init/Internal/Order/Basic.lean:486`), `Mutual.addPreDefsFromUnary` (`:196-220`, `Lean/Elab/PreDefinition/Mutual.lean:21-44`, `Lean/Elab/PreDefinition/Basic.lean:179-214`) adds a safe `.defnInfo` under `f` (for a single prefix-fixed definition) or `f.mutual` (for mutual or non-prefix definitions), and `addAndCompilePartialRec` (`:221`, `Lean/Elab/PreDefinition/Basic.lean:285-301`), when no definition of the block is a theorem or marked `noncomputable` (`shouldGenCodeFor`, `Lean/Elab/PreDefinition/Basic.lean:134-135`), compiles the recursive body through a `partial` `._unsafe_rec` helper that `toDecl` and `getDeclInfo?` (`Lean/Compiler/LCNF/ToDecl.lean:25-27,50-77`) select for code generation. For a block with a `noncomputable` definition it adds no helper, and the safe `.defnInfo` with `Lean.Order.fix` is added all the same. Where the helper is added, the base constant is a safe `.definition`, so that helper meets `HelperForm`, and without this clause the diverging `partial_fixpoint` definitions measured below passed `lake build --wfail` and `lake lint`. By contrast, `inductive_fixpoint`, `coinductive_fixpoint` (`PartialFixpoint/Main.lean:93-102`) and `coinductive` (`Lean/Elab/Coinductive.lean:480-498`) require `Prop`, use `CompleteLattice` and `Lean.Order.lfp_monotone` (`Init/Internal/Order/Basic.lean:324`) rather than `Lean.Order.fix`, and generate no runtime code (`shouldGenerateCode`, `Lean/Compiler/LCNF/Main.lean:31-49`). Unfolding a dependency's `partial_fixpoint` definition (such as `rw [Dep.f]`) asks `getUnfoldFor?` (`Lean/Elab/PreDefinition/PartialFixpoint/Eqns.lean:181-186`) for `Dep.f.eq_def`: if the environment already holds a constant of that name it returns that name and adds nothing; otherwise it looks up `eqnInfoExt` (`:30-35`, populated by `registerEqnsInfo`, `:74-87`, which registers non-theorem, non-`Prop` definitions and exports entries at `.exported`/`.server` only when `env.hasExposedBody`), returning `none` when no entry is present and calling `mkUnfoldEq` (`:140-179`) to add a `.thmInfo` in the module being elaborated when an entry is present. In the exposed dependency case measured below, `depSpin.eq_def` was added to the claimed module as a `.thmInfo` whose value directly mentions `Lean.Order.fix`. So, as the owner decided on 2026-11-20 ([the record](confirmation.md#2026-11-20-partial_fixpoint-under-rg1006)), RG1006 refuses claimed `.definition` and `.opaque` constants whose value directly mentions `Lean.Order.fix`, and this clause reads no `.theorem` declaration and not `Lean.Order.lfp_monotone`. The rule's other clauses still read each claimed constant: a theorem with a helper's name is reported (`rg1006_reports_named_not_partial`), and the exempted forms exempt a constant from the first two clauses only, so a definition or opaque constant of either form whose value mentions `Lean.Order.fix` is reported (`rg1006_exact`; `rg1006_admits_helper` and `rg1006_admits_ctorIdxImpl` take the absence of both mentions as hypotheses). Under the full gate, RG1010 already refuses `partial_fixpoint`, `inductive_fixpoint`, `coinductive_fixpoint` and `coinductive` before compilation (`lean/Regula/LanguageSet.lean`).

**Measured** on 2026-11-20 at Lean `v4.35.0` (macOS arm64) on disposable projects of `standard-logical` requiring this revision of Regula by path, after `lake build --wfail`: (a) a claimed module with a diverging `Nat → Nat` `partial_fixpoint` (`spinNat`), a diverging `Option Nat` `partial_fixpoint` (`spinOpt`), a non-prefix `partial_fixpoint` (`nonPrefix`), a `mutual` `partial_fixpoint` (`evenSpin`/`oddSpin`), a `where` `partial_fixpoint` (`withGo.go`), and a `noncomputable opaque` directly referencing `Lean.Order.fix` (`opaqueFix`) failed `lake lint` with exit 1 and 6 RG1006 findings (`spinNat`, `_private.Bad.0.withGo.go`, `opaqueFix`, `evenSpin.mutual`, `spinOpt`, `nonPrefix.mutual`) out of 22 claimed constants; (b) a claimed module with a `coinductive_fixpoint` predicate (`alwaysTrue`), an `inductive_fixpoint` predicate (`neverTrue`), a `coinductive` predicate (`InfStep`), and a theorem unfolding a dependency's `partial_fixpoint` via `rw [depSpin]` passed `lake lint` with exit 0 (24 claimed constants), and inspecting `Good.olean` confirmed as a positive control that `depSpin.eq_def` was realized in the claimed module as a `.thmInfo` whose value mentions `Lean.Order.fix`, while `alwaysTrue`, `neverTrue` and `InfStep` mention `Lean.Order.lfp_monotone` and not `Lean.Order.fix`.

What this leaves out, as accepted risk under the owner's trust in dependencies:

- A loop or `partial_fixpoint` inside a dependency or the toolchain, such as `IO.iterate` (`Init/System/IO.lean:780`), which is a `partial def` that a claimed constant can call. **Measured**: `IO.iterate` passes.
- A claimed function that takes a value of `Lean.Loop` as an argument mentions neither construct, and it passes (**measured**). Running it needs that value, which claimed code can make only through `Lean.Loop.mk`, so only a dependency's value runs it.
- A mention only in a constant's type, which runs nothing. **Proved**: `rg1006_admits_type_mention`, `rg1006_admits_fix_type_mention`.
- A mention of `Lean.Order.fix` in a theorem's proof, which runs nothing (**proved**: `rg1006_admits_fix_theorem`).
- A loop or `partial_fixpoint` that a claimed module's own code adds during the build, as a constant of an exempted form below (for a helper whose own value mentions neither a loop construct nor `Lean.Order.fix`).

**The exempted forms.** RG1006 admits two structural forms from its safety and helper-name clauses (never from loop constructs or `Lean.Order.fix`):

1. **The recursion-helper form (`Input.HelperForm`).** A partial constant `f._unsafe_rec`, not unsafe, with no `implemented_by` and no `extern`, in the module of a safe, total definition `f` with neither. It is the form of what Lean's elaborator adds for a safe recursive definition, which is why it is exempted, and it is a form and nothing else: the input holds nothing of who produced a constant. Lean makes the base of a `partial def` an opaque constant, so the rule reports the helper of a `partial def`.

**The branches of the compiler's two functions.** Read from the source at the pinned tag, branch by branch. `toDecl` has three: an `@[extern]` constant, a constant with an initialization function, and otherwise the value of the constant, or of `f._unsafe_rec` in the place of `f` when the environment holds one (`Lean/Compiler/LCNF/ToDecl.lean:68-77`, with `getDeclInfo?`, `:25-27` and `:52`), which RG1006 reads. `shouldGenerateCode` answers, in this order: no code for a constant that `isCompIrrelevant` gives, code for an `@[extern]` constant, no code for a constant that the environment does not hold or that has no value, for one with `@[macro_inline]`, for one with `@[implemented_by]`, for a matcher, for a constant that `isMatcherLike` gives and for one that `isCasesOnLike` gives, and code for every other (`Lean/Compiler/LCNF/Main.lean:31-45`). So `attribute [implemented_by g] f` after the declaration of `f` in its own module is read as the attribute on `f` is, and another module cannot add it to `f`.
- The query of an imported constant reads the entries of the module that holds the constant, and nothing else (`Lean/Attributes.lean:310-322`). An entry that another module's code writes into the extension directly, for a constant it imported, is read by neither the query nor the compiler, whose queries are the same.
- A module stores each entry at the level `.private`, and the `.olean` of a level below it only those of a public declaration (`Lean/Attributes.lean:258-263` and `:276-283`). The loader imports at the level `.private`, which reads each module's private data (`Lean/Environment.lean:2396` and `:2547`), and sets each module's entries whatever `loadExts` is (`:2742`). So a private declaration of a `module` file is read too.
- `@[init]` and `@[builtin_init]` are parametric attributes too, so the three statements above hold of them, with two differences (`Lean/Compiler/InitAttr.lean:50-79`). They keep the order of a module's entries, and a query takes the first entry for the name (`Lean/Attributes.lean:310-322`); `Facts.uninitialized` reads every entry for the name in the module's own entries. And at a level below `.private` a module's `.olean` holds the entries of `@[init]` only for a `meta` declaration, and every entry of `@[builtin_init]` (`Lean/Compiler/InitAttr.lean:74-79`, `:101` and `:110`); the loader imports at the level `.private`, which holds each entry.
- What Lean's own elaborators add is read as what a declaration states: the `unsafe` term (`Lean/Elab/BuiltinNotation.lean:578`), `deriving TypeName` (`Lean/Elab/Deriving/TypeName.lean:25`) and the computed fields of an inductive type, which replace its `casesOn` and constructors (`Lean/Elab/ComputedFields.lean:150` and `:171`), each give a constant that RG1011 refuses.

### RG1012: hidden panics

The rule refuses each definition or opaque constant of a claimed module whose value mentions a panic form. `Violates1012`, with `BangNamed` and `Input.PanicForm`, in [`RegulaSpecification/Rules/RG1012.lean`](RegulaSpecification/Rules/RG1012.lean). **Proved**: `rg1012_exact` in both directions, `rg1012_checker_refuses_panic` for a mention of `panicWithPosWithDecl`, and `rg1012_admits_theorems`, that neither a definition whose value mentions a theorem named with `!` nor a theorem whose proof mentions `Option.get!` is a violation. `bangNamed_hygienic` and `not_bangNamed_query` state that a name with macro scopes counts by the name they erase to and that `GetElem?.getElem?`, to which `xs[i]?` elaborates, is no panic form. In the terms of the environment, a pass gives, for each definition or opaque constant `n` of `Environment.constants.map₁` in a claimed module, that its value mentions no name of which `EnvPanic` holds (**proved**: `pass_iff`, through `EnvFloor`), and `pass_held` states the same of each claimed module's own constant as its `.olean` states it.

**Why.** A total function of Lean can still panic, and a panic gives the type's default value. In Lean's logic `panicCore` is `default` (`Init/Prelude.lean:3857`), and its compiled code prints the message and returns that default, unless the variable `LEAN_ABORT_ON_PANIC` is set or the program asked to exit on a panic (`lean_panic_impl` and `lean_panic_fn`, `src/runtime/object.cpp:176-207`), each read at the tag v4.36.0. So a proved function can go on with a value that its proofs never considered, with no signal but a message on the error stream.

**What a panic form is.** One of Lean's four panic functions, `panicCore`, `panic`, `panicWithPos` and `panicWithPosWithDecl` (`Init/Prelude.lean:3857` and `:3871`, `Init/Util.lean:59` and `:81`), or a constant that the input does not hold as a theorem and whose name's last string component, after `Lean.Name.eraseMacroScopes`, contains `!`. A name that the input does not hold counts, so a mention that the input cannot classify is refused. **Measured** on 2026-11-03 on a disposable module at v4.35.0, by reading what each form elaborates to in the constant's value: `xs[i]!` on an `Array`, a `List` and a user's `GetElem?` instance mentions `GetElem?.getElem!`; `Option.get!`, `List.head!`, `String.toNat!`, `Array.back!` and `Array.set!` mention themselves; `panic!`, `unreachable!` and `assert!` mention `panicWithPosWithDecl`; `xs[i]?` and `dbg_trace` mention none of these.

**Measured** on 2026-11-04 with this revision of the checker, on a disposable project of `standard-logical` that requires it by path, after `lake build`: `lake lint` read one claimed module and its 58 constants and reported RG1012 for exactly the 13 definitions that use a listed form: `xs[i]!` on an `Array`, on a `List`, on a structure whose `GetElem?` instance inherits the default `getElem!`, and inside a `where` function, which it reported as `rWhere.go`, the constant that holds the mention; `Option.get!` in a plain and in a `private` definition, reported as `_private.Probe.0.rPrivate`; `List.head!`, `String.toNat!`, `Array.back!`, `Array.set!`, `panic!`, `unreachable!` and `assert!`. It reported none of `xs[i]?`, `dbg_trace`, `xs[i]` with a `Fin` index, `Option.getD`, a theorem that states `x.get! = x.get!`, a structural recursive definition, the structure's derived instances and its `GetElem?` instance, nor `rWhere`, whose value mentions only `rWhere.go`. The verdict was `fail`, exit 1.

**Why a name, and why direct mentions.** [Issue 552](https://github.com/rbeauchamp/regula/issues/552) first framed the rule as refusing a constant whose value depends on `panicCore`. **Measured** on 2026-11-03 at v4.35.0: through what each constant mentions, 46,999 constants of Init and Std reach `panicCore`, among them `Std.HashMap.insert` and `List.mergeSort`, through the proof terms of `omega`, and through values alone 117 of Regula's own claimed constants reach it, through Lean's functions such as `Lean.Name.toString` and through `m[k]?` on a hash map, whose instance holds a `get!` field. `xs[i]!` on an array reaches no `panicCore`: `Array.get!Internal` is `@[extern "lean_array_get"]` with the value `Array.getD a i default` (`Init/Prelude.lean:3472-3474`), and its panic is in C (`lean_array_get_panic`, `include/lean/lean.h:1105-1135`). So a rule on reaching `panicCore` would refuse nearly all Lean code and Regula itself, and miss the most common form. The rule reads the name that Lean gives an operation that panics, as the owner's delegated agent decided on 2026-11-04 ([the record](confirmation.md#2026-11-04-the-rule-on-hidden-panics)). It reads only what a value mentions directly: on any path from a claimed constant to a panic form through the values of claimed definitions and opaque constants, the last of them mentions the form itself and is refused, so a build fails under that closure exactly when it fails under direct mentions.

**Measured** on 2026-11-04 over the 216,539 constants of the toolchain's Init, Std, Lean and Lake at v4.35.0, imported at the level `.private`: 523 constants that are no theorem have a name that `BangNamed` admits. For 472 of them, Lean's data shows a route to a panic: through the values of definitions and opaque constants, and from a constant to the one that `@[implemented_by]` names, each reaches `panicCore`, one of the 10 `@[extern]` constants among the 523, whose C code was not read, or `GetElem?.getElem!`, the one projection of a class's field among them, whose code is the instance's. The other 51 show no such route, so they cannot panic as far as Lean's data shows: 36 are syntax, such as the parsers, macro rules and unexpanders of `simpa!`, `grind!` and `xs[i]!`, which a program does not call, and 15 are functions, among them `Std.DHashMap.getEntry!`, `Subarray.get!` and `ByteSlice.get!`, and `Std.DHashMap.Internal.AssocList.getEntry!`, which returns `default` without a panic. A claimed definition that mentions one of these 51 is refused, though it cannot panic through it: a refusal within the published criterion, not a false refusal. 3,696 theorems of the toolchain have such a name and are no panic forms. Regula's own claimed definitions and opaque constants, 879 at the base of this change, mention no panic form, and on 2026-11-04 the local gate's `lake lint` passed on Regula's 23 claimed modules and 1,396 constants and on this package's 52 modules and 4,264 constants with RG1012 among the rules. The probe was a diagnostic and is not kept.

What this leaves out, under the owner's trust in Lean and in dependencies, and what [what a pass means](#what-a-pass-means) states:

- A panic inside the code of a dependency or of the toolchain, reached through a constant whose name has no `!`, such as `Lean.Name.toString`, or `outOfBounds`, which the default of `GetElem?.getElem!` calls (`Init/GetElem.lean:17-18` and `:107-108`).
- A panic in C code behind `@[extern]` of a constant whose name has no `!`. RG1011 already refuses `@[implemented_by]` and `@[extern]` on a claimed constant.
- A claimed `GetElem?` instance that inherits the default `getElem!` is not refused, because its value mentions `outOfBounds` and no panic form. Each `c[i]!` that uses it mentions `GetElem?.getElem!` and is refused instead.
- A mention in a constant's type, not its value.

Refused, outside the narrow purpose though within the criterion: a definition whose value mentions a constant named with `!` that is no theorem only inside a proof, which never runs, and a mention of one of the 51 constants above.

### RG1013: files that are not `module` files

The rule refuses each claimed module that is not one of the loaded modules that Lean read as a `module` file. `Violates1013`, with `Input.ClaimedModule` and `Input.ModuleFile`, in [`RegulaSpecification/Rules/RG1013.lean`](RegulaSpecification/Rules/RG1013.lean). **Proved**: `rg1013_exact` in both directions, and `rg1013_reads_modules`, that two inputs with the same claimed modules and the same `module` files have the same violations, whatever their constants and their profiles. Its subject is a module and no constant, so a finding of it prints the module alone, and it reports a claimed module that holds no constant. Under the full verdict the language check refuses such a file first, as RG1010 and before anything is compiled ([the closed set](#the-closed-set)).

The owner said yes to it on 2026-11-17 ([the record](confirmation.md#2026-11-17-the-check-for-module-files)). An importer that is a `module` file sees of a `module` file what its author chose ([Module files](#module-files)), so what a caller of a claimed module relies on is stated. The rule adds nothing to what a proof depends on: RG1001 to RG1006, RG1011 and RG1012 read each constant of a claimed module with its body, in a `module` file or not.

**What the input reads.** `Regula.Load.Facts.moduleFiles` lists each loaded module, claimed or not, whose data in the environment's header has the flag `isModule`, and the rule reports of them only a claimed one. **Proved** of the environment: `pass_iff`, through `EnvFloor`, states that the data at an index that has the name of each claimed module has the flag (`EnvModuleFile`). The import adds a module's name to the header only when it first meets that module, so a name has one index (read from the source: `Lean/Environment.lean:155-160` and `2568-2594` at v4.36.0). **Assumed** (`leanImport`): that the flag in the data is the one of the header of the environment that elaborated the file. Lean writes the flag into each part of a module's `.olean` from that header, and writes one part with it for a file that is not a `module` file (`ModuleData.isModule`, `mkModuleData` and `writeModule`, `Lean/Environment.lean:109-111`, `2224-2227` and `2243-2259`). The loader's import, at the level `.private`, loads the data of each module and keeps of a `module` file its private part and of another file its one part (`Lean/Environment.lean:2381-2398`, `2545-2547` and `2677-2681`). The header of that environment is a `module` one when the file's header has `module` or the setup that Lean is given says so (`Lean/Elab/Import.lean:26-27` and `141-160`, `Lean/Elab/Frontend.lean:294-313`, `Lean/Language/Lean.lean:502-505`, `Lean/Environment.lean:2672-2673`). Read from the source, and no verdict relies on it: Lake takes the setup's flag from the file's header, which it reads with `Lean.parseImports'` (`Lake/Build/Module.lean:49-58`, `688` and `723`, `Lean/Elab/ParseImportsFast.lean:237-238` and `251-254`). So for a build by Lake the rule refuses a claimed file whose header has no `module`, and a file that another tool compiles with a setup that sets the flag is admitted without it. The list holds the modules that have the flag, and not those that lack it, so a claimed module of which the loader read nothing is refused.

**What it costs a project**, which the owner was shown. Each claimed file needs the `module` header, and a proof that unfolds the body of a definition of another `module` file needs that body exposed or `import all`, as this package's own files show ([Module files](#module-files)). **Measured** on 2026-11-17: the three Lean files that `lake new app` writes at v4.35.0 have no `module` header. Read from the source: Lean refuses a `module` file that imports a file that is not one (`Lean/Environment.lean:2480-2484`), so a project whose claimed modules import, directly or through their imports, a file of a dependency that is not a `module` file cannot pass until that file is one. The rule reports no module of a dependency or of the toolchain. Lake's `requiresModuleSystem` does not replace the rule: the project itself sets it, `allowNonModules` turns its warning off, and Lake warns only of a file that imports a module of a package that set it ([Decisions of this specification](#decisions-of-this-specification)).

**Measured** on 2026-11-17 with this revision of the checker at Lean 4.35.0 on Ubuntu 24.04.5 LTS (x86-64), on a disposable project of `standard-logical` that requires the checker and a second package by path, after `lake build --wfail`. Of five claimed modules, `lake lint` reported RG1013 for exactly three, each as ``RG1013 Probe.Plain: the file is not a `module` file``, and exited with 1: a file with one theorem and no `module` header, an empty file, and a file with no `module` header that imports the second package's file, which is no `module` file either. It reported neither a `module` file with one theorem nor a file that holds `module` alone, and nothing of the second package's module. With the three files removed, it passed. A claimed `module` file that imports the second package's file did not build: ``cannot import non-`module` Dep from `module```.

### RG2001: the environment

A run that cannot load the build gives `incomplete`. So does an input that the admission refuses, a claimed module whose index is missing when reading its `@[csimp]` entries (`Facts.csimps`), a constant of a claimed module that the loader refuses (`Facts.unread?`), any argument list other than one profile, and any Lean other than the one this revision reads (`Regula.Shell.supportsLean`). In the full gate, so does each case of [the closed list](#the-closed-list-of-refusals) with exit 2. `gateRecord` in [`RegulaSpecification/Gate.lean`](RegulaSpecification/Gate.lean) states the verdict. **Proved**: `gate_o5`, so the record leaves nothing unsaid about the verdict, and `gate_adequate`.

The checker runs `Regula.Closed.Draft.admit` within `Regula.Load.Facts.prepare`, replays the claim's cone in Lean's kernel (`Regula.Shell.replayed`, `replayed_spec`), and evaluates `Regula.Closed.decisionPrepared` on that final load result. `decisionPrepared_eq` proves that report equal to `Regula.Closed.decision` on the corresponding input-or-error result when each admitted `Prepared` carries `Input.tables` of its input, which `Facts.prepare_tables` proves of what the loader gives. **Proved** of `Regula.Closed.Draft.admit`, `Regula.Closed.Input.report` and `Regula.Closed.decision`, in [`RegulaSpecification/Proofs/Verdict.lean`](RegulaSpecification/Proofs/Verdict.lean) and the registry, [`RegulaSpecification/Rules.lean`](RegulaSpecification/Rules.lean):

- `admit_ok_iff`, `admit_error_iff`: its admission refuses exactly a reading without `Input.WellFormed`.
- `run_refused`: a refused input is `incomplete`, where `run` is the admission and then the decision.
- `run_complete`: an admitted input is not `incomplete`, and it is `pass` exactly when every rule holds of it. `report_complete` states that of each value of `Regula.Closed.Input`, with no hypothesis, from the checker's own `Regula.Closed.report_pass_iff`, and `Regula.Closed.report_findings` states that its report holds exactly the findings of the registered rules, which `Regula.Closed.mem_findings` states.
- `run_meets`: the verdict meets `gateRecord`, with `none` for a build that the shell cannot load.

The exit code of `pass` is 0, and no other verdict has it (**proved**: `Regula.Closed.Verdict.exitCode_eq_zero_iff`). `fail` is 1 and `incomplete` is 2. A process that dies ends with a code of its own, which no theorem relates to a verdict, so only exit 0 reads as a pass.

**Measured** on 2026-10-31 on a disposable project that requires the revision of pull request 515, before the loader read what the import replaces. ## What a pass means

Regula gives one of two verdicts, and the last line of a run says which. This section is about the proof verdict. [The language check](#the-language-check) states the full verdict, which needs what a pass here needs and more.

A pass of the proof verdict is the result of two commands of the pinned toolchain on one finished build, in this order:

1. `lake build --wfail`.
2. `lake lint`, Regula's checker.

The first is Lake's own, and Regula makes no claim of its own about what it decides (**Assumed**: `lakeCommands`).

**The replay of the cone.** The checker loads the build, fills the closed input from it (below), and asks Lean's replay, `Kernel.Environment.replay`, to add the cone of the claim into the kernel's environment of `Lean.mkEmptyEnvironment`, which holds no constant (`Lean/Environment.lean:1848-1863`). A pass needs that replay to answer with success; any other answer is `incomplete` (RG2001). The cone starts at each constant of a claimed module and at each constant that Lean's kernel builds into a term that it checks and that the environment holds (`Input.kernelNames`): the types of a literal, what the kernel unfolds a number and a string literal to, and the values of its arithmetic on numbers (`Lean/Expr.lean:622-624`, `src/kernel/inductive.cpp:1347-1390`, `src/kernel/type_checker.cpp:665`, `src/library/constants.cpp:12-15`). It holds every constant that these reach through what each mentions, the relation `uses` of the closed input and `Mentions` of the specification: the type of each constant, the value of a definition, theorem or opaque constant, the constructors and the other types of an inductive type's block, the inductive type of a constructor, the types of a recursor's block, and `Eq` for a quotient. Lean's replay follows `ConstantInfo.getUsedConstantsAsSet` (`Lean/Util/FoldConsts.lean:67-74`), whose `Expr.getUsedConstants` also lists the structure of each projection (`Lean/Util/FoldConsts.lean:41`), reads each type of a block and its constructors (`Lean/Replay.lean:105-111`), and adds `Eq` before a quotient (`Lean/Replay.lean:129-133`). The replay is given each constant of the cone as the environment keeps it, but `Quot.mk`, `Quot.lift` and `Quot.ind`, which the kernel adds with `Quot` and refuses to add again (`src/kernel/quot.cpp:50-56`), as `leanchecker` leaves them out (`src/LeanChecker.lean:68-71`).

- **Proved**: `mem_cone`, that the checker's search gives exactly what its seeds reach; `mem_cone_env`, that this is `InCone`, the cone in the terms of the environment; `replayConstants_env`, that what the replay is given is exactly the cone, each constant as `Environment.constants.map₁` keeps it, but the companions of `Quot`; `inCone_mentions`, that the cone is closed under what its names mention; `claimed_inCone`, that each constant of a claimed module is in it; `claimed_theorem_replayed`, that each theorem of a claimed module, as its own module states it, is the kept constant by `==` or is given to the replay under a name of its own, with `copy_name_fresh`, that no constant of the environment has such a name, and `copyEntries_nodup`, that no two copies share one; `kernelNames_eq`, the list stated as a literal apart from the checker's; and `plain_exit_zero` and `full_exit_zero`, that exit 0 needs the replay's success on that map, by `Replayed`, for every response.
- **Assumed** (`replay`, `kernel`, `h6`): that Lean's replay answers with success only when Lean's kernel accepted each constant of the map that is neither unsafe nor partial, each after the constants of the map that it mentions, with each constructor and recursor equal to what the kernel made of its inductive type, and that a constant that one of them mentions and that the map does not hold is unknown to the kernel, which refuses what mentions it (`Lean/Replay.lean:59-63`, `74-140`, `148-190`). For no false refusal, that the kernel looks up no constant beyond those that the cone follows and `Input.kernelNames`.

So, for a project that places no file or code aimed at the checker or the toolchain, a pass means that the proofs of the claimed modules are sound, checked by Lean's kernel in an environment that holds the cone of the claim and nothing else, and that each axiom they reach through what each constant mentions is one that the profile allows (RG1002 to RG1005, over the same relation). A project that may be aimed at the checker needs the full verdict, as [a project aimed at the checker](#a-project-aimed-at-the-checker) states. An unsound proof in a dependency that the claim reaches fails the replay, as one in a claimed module does. The replay skips each partial or unsafe constant, as Lean's replay does (`Lean/Replay.lean:182`): RG1006 refuses each such constant of a claimed module unless it has an exempted form (`HelperForm` or `CtorIdxImpl`, whose value RG1006 still checks for loop constructs and, for a definition or opaque constant, `Lean.Order.fix`), and the kernel refuses a safe constant that mentions one (H6). Lean's import keeps one of the theorems of one name and type that its modules state, the last, and gives the name the first module's index (`subsumesInfo` and `finalizeImport`, `Lean/Environment.lean:2633-2639`, `2700-2709`). So the replay also gets each theorem that a claimed module's own data states and that `==` does not relate to the kept one (`Facts.copies`), under the name `root.k`, whose root has more components than any name of the environment (`copyRoot`). Its value's mentions are in the cone, because the cone also starts at each name that a claimed module's own data states, and what a name mentions includes what each copy of it mentions. **Measured** on 2026-11-02: in a project whose two modules each rewrite with `f.eq_def`, Lean regenerated that lemma in both, and the copies differ from the kept one under `==`, as 16 copies of Lean's own library loaded there do, so refusing such a copy would refuse ordinary projects. What only `Input.kernelNames` reach is replayed and is no part of the claim, so its axioms are not counted, as `#print axioms` does not count them: the kernel needs those constants declared to check a term that holds a literal, which mentions none of them.

RG1011 refuses each constant of a claimed module that has `@[implemented_by]` (other than the verified safe half `T.ctorIdx` of a compiler-generated `ctorIdx` pair, covered by `ctorIdxTag`) or `@[extern]`, each definition of one for which `@[init]` or `@[builtin_init]` names an initialization function, and each exported (`global` or `scoped`) `@[csimp]` entry registered in a claimed module whose theorem is not declared in any claimed module's `.olean` data (`moduleData`), so a pass says that no unexempted replacement attribute replaces the compiled code of a constant of the claim that the environment keeps, that no initialization function replaces the value of a definition of the claim that it keeps, and that every exported `@[csimp]` entry registered in a claimed module targets a constant declared in some claimed module. Beyond that it says nothing about what a compiled program runs. A claimed module can still use exported `@[csimp]` on a theorem declared in a claimed module (whose safe proof the kernel checks in the claim's cone within the profile, while RG1006 refuses `unsafe` and `partial` claimed constants without an exempted form), `attribute [local csimp]` (`.olean`-invisible, never written to `.olean`) and dependency-registered `@[csimp]` (in unclaimed modules, not checked by RG1011) stay outside the proof verdict (under the full verdict RG1010 refuses `csimp` in each file it reads, a project with a `require` has only the proof verdict, and the toolchain's own `@[csimp]` registrations stay trusted), a claimed module's own code can add a constant of an exempted form during the build, whose form RG1006 reads and whose value RG1006 reads only for loop constructs and (for a definition or opaque constant) `Lean.Order.fix`, not for what else a recursion helper computes, and a claimed constant can call a dependency's or the toolchain's constant that has either attribute or an initialization function. [RG1011](#rg1011-replaced-compiled-code) states what it reads and leaves out. **Measured** on 2026-10-31, before RG1011: a module with each of `@[implemented_by]`, `@[extern]` and `@[csimp]` passed `lake build --wfail`, `lake check` and `lake lint`.

RG1012 refuses each definition or opaque constant of a claimed module whose value mentions a panic form, so a pass says that no such value mentions one of Lean's four panic functions or a constant that is no theorem and that Lean names with `!`. A claimed function can still reach a panic inside the code of a dependency or of the toolchain, through a constant whose name has no `!`, or in C code behind `@[extern]` of such a constant. [RG1012](#rg1012-hidden-panics) states what it reads and leaves out.

RG1013 refuses each claimed module that Lean did not read as a `module` file, so a pass says that the `.olean` of each claimed module states that its file is one. A pass says that of no other module: that a `module` file imports only `module` files is Lean's own refusal, and no theorem here.

**Measured** on 2026-10-31, before the checker replayed anything: a module that added a theorem of `False` with `set_option debug.skipKernelTC true` passed `lake build` and `lake lint`, and `lake check` refused it. **Measured** on 2026-11-02 on a disposable project at Lean 4.35.0: `lake check --inadvisably-no-sandbox` passed a module that added, under that option, a theorem `hidden._bad : False` whose name Lean marks as internal (`Name.isInternal`, `Lean/Data/Name.lean:125-128`) and that nothing mentions, because `lake check` exports from each constant whose name is not internal (`LeanExport/Basic.lean:463-474`). The checker of the release `v0.12.0` passed it too, with exit 0, and `lake build` printed no warning, so the three commands of that release passed a theorem of `False`. The checker of this revision gave `proof verdict: incomplete (RG2001)`, exit 2, with Lean's answer `(kernel) declaration type mismatch, 'hidden._bad' has type True but it is expected to have type False`, and on the same project without that theorem it passed.

### A project aimed at the checker

The two commands of the proof verdict run in the project's own Lake, which loads what the project placed and runs its code. So what a pass means, above, holds for a project that places no file or code aimed at the checker or the toolchain. A project that may be aimed at them needs the full verdict. A project with a dependency or with Mathlib in its imports gets only the proof verdict, so Regula gives no verdict that holds of such a project if it is aimed at them. A project aimed at the checker can make `lake lint` print a pass and exit 0 whatever its build holds, an unsound proof included, by each of these routes, and the full verdict closes each:

| Route | How it reaches the proof verdict | How the full verdict closes it |
| --- | --- | --- |
| A library under a leaf name that the checker uses, such as `libc++.1.dylib` on macOS or `libc.so.6` on Ubuntu, in the project's library directory | `lake lint` starts the checker with `DYLD_LIBRARY_PATH`, or `LD_LIBRARY_PATH` on Ubuntu, naming the toolchain's library directories and then each package's, the project's `.lake/build/lib` by default (**Assumed**: `lakeStart`), and the loader takes a library by its leaf name from such a directory before the paths that the checker records and the system's (**Assumed**: `processes`). A library built to resolve its own dependencies runs its initializers in the checker before `main`, so it can print any line and exit 0, argued from dyld(1), and on Ubuntu from elf(5), whose `.init` code the system runs before the program's entry point. No code of the project has to run first. **Measured** in [what was measured](#what-was-measured), and on Ubuntu in [Ubuntu](#ubuntu). | Its checker starts from a checkout built apart from the project, so its search path names the toolchain's directories, the checkout's and what the operator's own environment holds, and its Lake commands start through `/usr/bin/env -i` with no such variable (`spawnLake_eq`). **Measured** in [what was measured](#what-was-measured), and on Ubuntu in [Ubuntu](#ubuntu). |
| A doctored copy of Regula | `lintDriver` names an executable as the project's workspace resolves it (`Lake/CLI/Actions.lean:89-100`), so the project's configuration, manifest and package directory choose the copy that runs, and Lake keeps a checkout in the package directory that is at the manifest's revision with only a warning of local changes (`Lake/Load/Materialize.lean:44`, `:55-58`, `:106-107`). ### Noncomputable definitions

No rule of Regula reads whether a declaration is `noncomputable`, and no profile separates classical proofs from `noncomputable` definitions, by [the owner's decision of 2026-11-20](confirmation.md#2026-11-20-noncomputable-definitions). `Lean.Parser.Command.noncomputable` and `"noncomputable"` remain admitted in RG1010's tables ([`lean/Regula/LanguageSet.lean`](../lean/Regula/LanguageSet.lean)). A pass of either verdict therefore states nothing about whether a claimed definition has compiled code, beyond RG1011's refusal of unexempted `@[implemented_by]`, `@[extern]`, an initialization function (`@[init]` or `@[builtin_init]`) on a claimed definition, and exported claimed-module `@[csimp]` entries targeting theorems not declared in any claimed module.

Read from the source at Lean `v4.36.0` (relied on by no verdict):

- **Tag storage:** `getNoncomputableReason` does not exist in Lean `v4.36.0`. Lean stores a boolean tag in `noncomputableExt` (`Lean/Compiler/NoncomputableAttr.lean:16-26`), exported uniformly across `.olean` parts (`Lean/EnvExtension.lean:53-55,93-134`) and populated under `loadExts := false` at `.private` (`Lean/Environment.lean:2742,2773`). Lean sets the tag when a declaration is marked `noncomputable`, when compiling a declaration fails inside a `noncomputable section`, or when delta deriving (`processDefDeriving`) adds a data-valued instance under `deriving noncomputable instance` or inside a `noncomputable section` (`Lean/CoreM.lean:941-946`, `Lean/Elab/PreDefinition/Basic.lean:138-141,220`, `Lean/Elab/MutualDef.lean:1214-1217`, `Lean/Elab/Deriving/Basic.lean:243-261`). Delta deriving of a `Prop`-valued instance takes the theorem branch, which sets no tag (`Lean/Elab/Deriving/Basic.lean:236-242`); class deriving handlers (dispatched when every target is an identifier and none names a definition, `:361-377`) were not read for this record.
- **Compiler check on references:** `checkComputable` (`Lean/Compiler/LCNF/ToLCNF.lean:440-455`) is called from one place, `visitAppCore` (`:944-946`), inside `toLCNF`, and `toLCNF` is called from one place, the branch of `toDecl` that compiles a constant's value (`Lean/Compiler/LCNF/ToDecl.lean:76-82`). So it reads only a body that Lean compiles, and none that the next entry lists. In such a body, proofs (`Prop`) and type formers are erased (`Lean/Compiler/LCNF/Main.lean:31-32,47-49`, `Lean/Compiler/LCNF/ToLCNF.lean:619-653`), and at each application `visitApp` first runs `constantReplacer` (`Lean/Compiler/LCNF/ToLCNF.lean:517-540,938-942`), which puts `f` for `f._unsafe_rec`, inlines a matcher, puts its replacement for a constant that `@[csimp]` replaces, and puts its value for a constant with `@[macro_inline]`, and visits the result instead. Only when none of these applies does `checkComputable` read the constant at the head of the application, and it rejects one tagged `noncomputable` or whose `_unsafe_rec` helper is tagged `noncomputable` (as happens when compiling a recursive definition fails inside a `noncomputable section`), unless the reference is in an erased constructor parameter (`:799-804`), the constant is `Quot.mk`, `Quot.lift` or `withPtrEq`, or the constant has `@[extern]` or `@[implemented_by]` (`:441-445`). The rule is therefore over each reference that remains in a computationally relevant position, after that rewriting and erasure, in a body that Lean compiles, and not over every definition that calls a `noncomputable` one. A constant that `@[csimp]` replaces or that has `@[macro_inline]` is never the name it reads, so a `noncomputable` constant of either kind is checked only through what replaces it; this is read from the source and was not measured. Downstream, `ToImpure` lowers the application using the arity from the referenced constant's impure signature or, if that signature is absent, from its monomorphic declaration (`Lean/Compiler/LCNF/ToImpure.lean:158-163,253-261`). Only when both are absent does it inspect the constant kind and reject a constant that the environment gives as an axiom, a quotient constant, an inductive type or a theorem (`:165-166,214-216`, such as a non-exposed imported `noncomputable @[extern]` constant). `IR/Checker` rejects calls to declarations lacking executable code (`Lean/Compiler/IR/Checker.lean:41-45,95-105`).
- **Replacement attributes:** `toDecl` (`Lean/Compiler/LCNF/ToDecl.lean:68-75`) skips compiling the body of a constant with `@[extern]` or an initialization function (`hasInitAttr`), and `shouldGenerateCode` (`Lean/Compiler/LCNF/Main.lean:40`) skips a constant with `@[implemented_by]`, so `checkComputable` reads no reference in such a body. RG1011 (with loader checks under RG2001 for hidden module-local entries and missing claimed module indices) refuses unexempted `@[implemented_by]` and `@[extern]` on claimed constants, `@[init]` or `@[builtin_init]` naming an initialization function on claimed definitions, and exported claimed-module `@[csimp]` entries targeting theorems not declared in any claimed module ([RG1011](#rg1011-replaced-compiled-code)).
- **Default `lean_exe` and `noncomputable def main`:** `emitMainFnIfNeeded` (`Lean/Compiler/LCNF/EmitC.lean:1084-1152`) emits C's `int main` (`:1120`) only when `main` appears in `getLocalDecls` with `.code`. A `noncomputable def main` (or `main` inside a `noncomputable section` whose compilation fails) therefore emits no C `main`. On non-Windows platforms, default `lean_exe` targets link Lean statically (`LeanExe.sharedLean`, `Lake/Config/LeanExe.lean:113-114`; `LeanExe.recBuildExe`, `Lake/Build/Executable.lean:22-35`; `mkLeanLinkArgs` and `buildLeanExeSync`, `Lake/Build/Common.lean:963-969,1101-1116`; `LeanInstall.ccLinkFlags`, `Lake/Config/InstallPath.lean:142-143,171-172`; `getLinkerFlags'`, `Lean/Compiler/FFI.lean:49-50`). ## The language check

Before anything is compiled, the check reads each Lean file Lake would compile for the claim, and the project's Lake configuration, and refuses anything outside a closed set. If it admits the project, the gate builds it, replays the cone of its claim and runs the rules on the result. A project whose Lake configuration has a `require`, or with Mathlib in its imports, can have only the proof verdict: the gate says so, builds nothing and exits with 3, and the operator gets that verdict with the two commands of [what a pass means](#what-a-pass-means) in the project, which run the project's code and its dependencies'.

The gate is `REGULA_FULL=DIR lake exe lint PROFILE`, from a checkout of Regula built apart from the project. Lake loads a project's configuration before anything Lake starts can run, and a `lakefile.lean` that runs can delete itself or plant a checker, so a run that the project's Lake started says nothing that can be trusted of a project aimed at the checker, as [a project aimed at the checker](#a-project-aimed-at-the-checker) states of the proof verdict. Starting the checker from its own package is a precondition of the full verdict, beside the `PATH` it runs with, and a start from a project's Lake is outside this contract. Regula does not test it: a project's code that ran first can make any program print any line, so a test would be no defence against what it is for, and a checkout whose `.lake` is a link shows that such a test can refuse a healthy start. [The confirmation record](confirmation.md#the-language-check) holds the restatement that the owner confirmed, the status of each consequence, and the second reading. The formal statement is `languageRecord` and `fullGateRecord` in [`RegulaSpecification/Language.lean`](RegulaSpecification/Language.lean).

**What selects what is audited.** The arguments of a run are one profile, and anything else is a refusal (`run_other`). A project's Lake configuration sets the arguments of its lint and test drivers (`lintDriverArgs`, `testDriverArgs`, `Lake/CLI/Actions.lean:71-100`), so it can name a profile and no directory. ### H1 and H2

These are hypotheses about what Lean v4.36.0 does. They are stated in `LeanBehaviour`, never as axioms. No proof in Lean can reach them, because `Lean.Parser.parseCommand` is `partial` (`Lean/Parser/Module.lean:135`) and Lean's elaborator has no model here. The owner confirmed that a hypothesis of this kind, re-read at each upgrade of Lean, counts as Lean staying trusted. So "no bugs" here means no bug outside these stated, version-bound claims.

**H1: the tree the check read is the tree Lean elaborates.** The frontend calls the same `parseCommand`, with state from the elaborator (`Lean/Language/Lean.lean:595-601`). The parser reads that state only as scoped parser entries and tokens (`Lean/Parser/Extension.lean:607-612`, `Lean/Parser/Module.lean:124,146`), the option `internal.parseQuotWithCurrentStage` in quotations, the options `doc.verso` and `doc.verso.module` in doc comments (`Lean/DocString/Parser.lean:2239-2240`, `:2264-2271`, `Lean/Parser/Term.lean:214-215`, `Lean/Parser/Command.lean:60-61`), and namespace and open declarations when it resolves a parser's name in a quotation (`Lean/Parser/Extension.lean:765`). Quotations and the first option are refused. The two options of doc comments are not in the admitted `options` (**proved**: `Assumption.verso_options_not_admitted`), so an admitted file is parsed with both unset, as the reader parses it. Scoped entries activate only at `open` and `namespace` (`Lean/Elab/Open.lean:83,89,101`, `Lean/Elab/BuiltinCommand.lean:60`), and no target of an admitted file can activate a namespace that holds any. No admitted command adds a parser, so the project's own modules add none to the environment. ### What remains

**Not closed, by design**, each [outside the contract](#outside-the-contract) or outside [the named configurations](#the-named-configurations):

- Another process that changes the checker's tree.
- A start from a project's Lake, with project code that ran first.
- A `lake -d` or a `lake -f`, on which a pass is about the current directory and not what the option named: [Lake gives a program nothing to tell them by](#the-language-check).
- A call that does not return.
- A `REGULA_FULL` left set in the environment of a `lake lint`, which is the request of whoever started the run and an accepted risk: the run gives the full gate on the directory it names, and its last line says so. Testing who started a run is what would close it, and `lake lint` and `lake exe` start a program through one environment with nothing to tell them apart (`Lake/CLI/Actions.lean:20-21`, `:98`, `Lake/CLI/Main.lean:1298`).
- A counterfeit `lake` or `lean` at the toolchain that `LEAN_SYSROOT` names.
- A process that changes the project after the read cannot reach the verdict, which is about the text read.
- Anything about a dependency's code, since a project with a dependency has only the proof verdict.
- The entries of the list of assumptions.
- A fake toolchain or a `PATH` shim: the check runs inside what it is given, and `supportsLean` reads only what that program says of itself.
- A checker that the operator did not build apart from the project.

**Accepted risk:**

- A project with a default executable, a `srcDir` on a target, or a source directory outside the closed names gets no full verdict until it is rearranged, which the owner confirmed, and its proof verdict stays.
- A project that needs a file outside its Lean sources and Lake configuration during the build fails its full verdict, visibly, and one full verdict costs one fresh build.
- A project with a harmless dependency gets only the proof verdict, and a harmless name outside the closed domain is `incomplete`.
- A harmless link that a project's source is read through gets no full verdict, and neither does a library with a recursive glob over its own directory: each is visible, and the cost is to name the modules.
- A link in a file that no root and no import reaches is not read, so nothing selects it and it does not change the verdict.
- The plain `lake lint` keeps Lake's own load and listing, because it gives only the proof verdict and Lake has already loaded the project there.
- An `instance` that changes what a statement means.

**Known failures that the check reaches:**

- [#462](https://github.com/rbeauchamp/regula/issues/462): `macro_rules` and `@[local macro]` are refused, and `match.ignoreUnusedAlts` is not in `options`. Closed for a full verdict.
- [#468](https://github.com/rbeauchamp/regula/issues/468): its macro cannot exist. No other form was found, and none was proved absent.
- [#469](https://github.com/rbeauchamp/regula/issues/469): no failure of what Regula claims. **Measured** on 2026-10-31 at this revision: a project's `isEmpty` on `Substring.Raw`, then `variable (s : Substring.Raw) (h : isEmpty s = true)`, `namespace Substring`, `include h`, `def usesH`, gets a full verdict while Lean discards the deprecation warning of the second elaboration, and a declaration with the same binders directly fails `lake build --wfail`. Regula makes no claim about warnings, since `lake build --wfail` is Lean's own, so that verdict is true of what it states. Refusing `variable`, `include` and `omit` is the one way to change this, and the owner's words admit them.
- [#471](https://github.com/rbeauchamp/regula/issues/471): `try?`, `exact?`, `apply?`, `#check_failure` and `#guard_msgs` are refused. Closed for those. Other places where Lean drops a message are unread, so no statement says that no message is dropped.

### Decisions

Each of these was decided on the owner's behalf, and [the confirmation record](confirmation.md#the-language-check) gives the rest:

- One process runs the check, the build, the replay of the cone and the rules, because a record that a first command left could be forged by project code in the build that a later command read. So the order is a program's order, with a theorem.
- The table is what real code uses, not every construct that meets the criterion, because each entry is a claim that H2 rests on. Regula's core uses about 170 of its kinds, and the rest go with library code of two other projects of the owner's that is outside this repository.
- The specification package stays outside this check. It imports lean-intent, whose files use `syntax` and `macro` (which RG1010 refuses). (It formerly also set `doc.verso` in `specification/lakefile.toml` until the [2026-11-21 ratcheted comment ban](confirmation.md#2026-11-21-ratcheted-comment-ban-option-r1) retired `doc.verso` and `linter.missingDocs` in both packages.) So it gets the proof verdict, and its proofs are still replayed, by the checker.
- The language decision reports each offending position and the shell prints at most 50, because a project far outside the set would otherwise print its whole tree.
- `Regula.Reader` and `Regula.Shell` are in the default target `RegulaChecker`, so a full verdict on Regula reads them, and every function of the checker that does not itself call Lake is in a default target too. They ask what calls Lake through the operations of `Regula.Effect`, and `Regula.Workspace` holds only those calls (`LakeCalls`). `Regula.LintMain` stays the thin `unsafe` root, because `Lean.enableInitializersExecution` requires it. `Regula.DiagnosticsGate` and `Regula.TestListing` are repository programs, not the checker.
- A library's or an executable's name must be in the closed domain, like a module's, because Lake joins an executable's name onto its output directory, and an absolute one selects a path outside the project. The root package's own name is not tested, because a default build uses it for no path. So a target named with a hyphen is `incomplete` until it is renamed, which is the cost of a closed domain.
- The configured paths and targets are a closed domain: each source directory lies below the tree with closed names, each `globs` entry is a single module, and each default target is a library, before any Lake call asks for the modules. A closed domain costs less than arguing about an open one. It refuses, as a configuration fault, and does not give `incomplete`, because the project's configuration states the path and nothing failed to read. `Reading.openPaths` holds each report, so a refusal with no reason is no state of the type.
- Every child of the gate works in a tree the checker made, and the checker reads the project by itself, on the owner's delegated agent's decision, because a list of the paths that Lake derives from a project's directory is the wrong shape, however complete it reads today, and a later Lake can add a row. The cost is one fresh build per full verdict, and a project that needs another file during its build fails. A project may keep its own `.lake`, since nothing reads it.

## Module files

Each Lean file of the root package is a `module` file. An importer that is a `module` file sees the type of a definition and the statement of a theorem, and it sees a body only where the author chose that: an `abbrev`, an instance or `@[expose]`. So what such a caller relies on is stated. **Measured** on 2026-10-31: Lean's header parser (`Lean.Parser.parseHeader`, `HeaderSyntax.isModule`) reported `module` for each of the 21 tracked Lean files below `lean/` at that date. Each added since, `Regula.ProgramCheck.EffectScan`, `Regula.Rule` and each rule's module below `lean/Regula/Rules/`, starts with `module` too, which the gate's build of it reads. Since RG1013, the gate's `lake lint` of each package refuses a claimed module of it that is not one.

The root package's `@[expose]` are on `Regula.ExecutableContract.run`, on `Regula.Effect.Resp`, on each rule's value `Regula.Rules.RGnnnn.rule`, so that the registry reads its spelling (`Regula.Closed.spellings_nodup`, by `decide`), and on `Regula.Closed.Report.verdict` and `Report.findings`, so that the registry proves what a report holds (`Regula.Closed.report_pass_iff`). A rule's check stays unexposed. The one on `Regula.ExecutableContract.run`: the exported theorem `ExecutableContract.run_eq` is proved by `rfl` over that body, and without the attribute it does not build. **Measured** on 2026-10-31. The one on `Regula.Effect.Resp`: a caller gives a program of an operation the type of its response, which only that body shows. Before this package's own change only `RegulaSpecification.Input`, which imports nothing, was one here ([the record](confirmation.md#2026-11-17-module-files-in-three-steps)).

Each file of this package that declares anything, 52 of the 53, holds its declarations in one `@[expose] public section`, so an importer sees the body of each definition: in such a section Lean exposes each `def` (`Lean/Elab/MutualDef.lean:1349-1356` and `:1386-1390` at v4.36.0). Each import is `public`, but the lines of `import all` below and one line of `RegulaSpecification.Assumptions`, `meta import Lean.Elab.Command`. ## Decisions of this specification

Each of these was decided on the owner's behalf by the owner's delegated agents, because the owner's intent asks for the smallest core that does the job. None is the owner's confirmation.

- The root package does not set Lake's `requiresModuleSystem`. Lake would then warn on each file that is not a `module` file and imports one (`Lake/Build/Module.lean:450-458`), so another project that imports `Regula.Contract` from such a file would need `allowNonModules`, and a file that imports nothing of the package would still not be seen. A `module` file that imports a file that is not one is already refused by Lean, and a file that stops being a `module` file is cheap to correct.
- The root package does not set `allowImportAll`, though this package's files use `import all` on its modules. Lake's two checks that read the field are disabled at this toolchain, and the language check, which the gate runs on the root package, admits no such key of a `lakefile.toml` (`Regula.Language.configKeys`). The gate ties those two: its run of the full gate on this checkout refuses the file while it holds a key that the table lacks.
- This package documents, names or proves a definition as the content of a file of the repository only when a build that the gate runs fails once the two differ. So `localSteps_eq`, `noCommentsVersion_eq`, `noCommentsArgs_eq`, `noCommentsTargets_eq`, and `kernelNames_eq` each prove a literal equal to the definition of the checker's package that it restates, and the pinned toolchain's text in `readingOf` of [`Proofs/Owner.lean`](RegulaSpecification/Proofs/Owner.lean) is the one that `admits_library_code` needs `Regula.Language.leanToolchain` to be. A definition here is a statement, a model or a case that a proof of another file may unfold, nothing in this repository outside the package imports it, and one rule for each file is the smaller. The checker's type holds what the rules read of it, and `Draft.admit` is the one place that decides the two parts that a real build can lack: a claim of no module and a mention of a constant that the input does not hold. The closed type `RuleId` is gone: a rule is its value in the registry, so it cannot lack a function, and `Regula.Closed.spellings_nodup` keeps each code naming one check. ## The run of the checker

The checker's whole run is a value of the type `Regula.Effect.Prog`, `Regula.Shell.run`: a tree whose every node names one operation of the closed type `Op`, with what to do for each response that operation can give. The tree performs nothing. `Prog.interpret` runs it, in `BaseIO`, through one table, `Regula.Effect.table`. An operation that can fail gives its failure as a value of its response, so `BaseIO`, whose type holds no exception, leaves the tree one way out: its leaf.

`Runs p t a` says that for the responses that the events `t` hold, `p` asks exactly the operations of `t`, in that order, and ends with `a`. A response is any value of its type, so a statement over `Runs` holds for every answer of Lean, Lake and the operating system, a failure included. It is a fact about what the run received and what it did with it, so `run_meets` and each theorem without `OneRealPath` rest on no file system staying still: another process can change any file between any two reads and back, and the statement holds of what the run read.

**Proved** of the definition that the executable runs, in [`RegulaSpecification/Proofs/`](RegulaSpecification/Proofs/), with the statement in [`Effects.lean`](RegulaSpecification/Effects.lean), [`EffectsRun.lean`](RegulaSpecification/EffectsRun.lean) and [`EffectsRecord.lean`](RegulaSpecification/EffectsRecord.lean). The original statements preceded the program; the preparation relations and `written` strengthen the record, and the reader was changed for the second so that it writes a module's file only for an admitted reading. `run_meets`, for every argument list and every response (`RunMeets`):

- **Refusal.** A Lean other than the pinned one, or an argument list other than one word, or a text that is no profile: exit 2, the last line of an incomplete proof verdict, and the run only says so (`Refusal`).
- **The proof verdict.** The exit code is that of `Regula.Closed.decision` on what the load gave, and so is the last line but for the directory that a pass names at its end, and the load gave what the proved `Facts.input` gives on the environment, the places and the modules that Lean and Lake returned, or an error for a case of `PlainReason`, each of which is what a response said about an operation that this load needs (`PlainRun`, `Loaded`, `BuildRead`). `PlainPreparation` directs the workspace load by earlier responses and each lookup or rules import after it names its root's `leanPath` as its search path. It requests no tree mutation. Exit 0 gives `EnvForm` and `EnvFloor` of what they returned (`plain_exit_zero`), and that no answer failed.
- **The check.** It admits only on a reading inside the closed language, and any other outcome rests on a `Reason`. An admitted reading rests on `Evidence`: the real path of the project and the tree, which lie apart; `lean-toolchain`; `lakefile.lean` absent by its name; each key path of `lakefile.toml`, whose text stands in the tree; the pinned text as the tree's `lean-toolchain`; for each file (`ReadText`), that it passed the exact-path test, that Lean's parser gave its header and commands from the text that `readFile` returned, in the environment of exactly the toolchain modules that `Sees` states, and that the tree holds that text at the file; and that the tree holds no text other than these. What `Evidence` calls held is `written`, a fold of the run's own writes and removals over the whole reading, so a text a later write replaced is not what the admission rests on. `ReadBack` then says that each such text is what the file system answered, for the path it was written at, in a last segment of the reading that holds no act, so each text the fold credits is also what the file system answered, and that the same segment holds its answer that nothing has the name `lakefile.lean` in the tree. That no other file is in the tree is still a statement of the fold, and rests on `createTempDir`. Any other outcome rests on a `Reason`, a closed set of what the responses said about what the requested build needs, by what the run has been told of that build (`Scene`, `Named`, `Needed`): a read of anything else justifies nothing. So a reader that refuses without one does not meet the record. On an admission, no read failed (`readProject_no_failed`).
- **Nothing is built unless the check admitted.** The events of the check hold no Lake command and no load for the rules (`only_readProject`). On any other outcome the gate asks nothing more.
- **Writes.** Each act of a full run, each `writeFile`, `createDirAll`, `removeDirAll` and the working directory of each Lake command, lies at or below the tree or is the tree, and, when any act lies below the tree, the two real paths lie apart, so a run writes nothing to the project's directory (`Confined`). When the only act is at the tree itself, that it holds nothing of the project rests on `createTempDir`. Every write asks `Regula.Reader.inTree` first.
- **Preparation at each occurrence.** `ReadingPreparation` fixes the complete acts of the reading: the TOML copy from an earlier source read, the pinned `leanToolchain` copy, the configuration load, and module copies, with each lookup and parser import naming that load's `root.toolchain` as its search path. Each `CopyStep` creates only its path's parent, when present, and writes only after that succeeds. A failed directory ends the step; a failed configuration copy ends the acts, while the grammar lets a failed module copy be followed by later module steps, which `Regula.Reader.writeSources` does not ask. A path or parent outside the tree makes no act. Every module step has `Named`, `FileOfModule` and `SourceText` from its preceding prefix; repeated names or paths need that provenance again. A lookup or an import carries its search path in its request, so no order of the run's acts decides which path it asked on. `readProject_spec`, `inputOf_spec`, `loadTree_spec` and `loadPlain_spec` prove the relations on the actual definitions' exact traces, each in the one statement of its stage, and compose into `run_meets`, so legitimate failures remain admitted. The acts of a reading lie in the tree by this grammar alone (`ReadingPreparation.readActs`).
- **Build and reload.** `BuildProtocol` permits exactly one build, using the identified Lake in the allocated tree, with only reporting around it. `BuildAndRules.no_mutation` excludes explicit writes, directory creation, allocation and removal from both the build and reload phases. `RulesPreparation` directs the reload by the received real path, and each rules import or lookup names the loaded root's `leanPath`. `build_protocol`, `rules_spec` and `loadTree_spec` prove these constraints for the actual definitions on every response; none describes filesystem effects inside trusted Lean/Lake calls.
- **Removal.** On every way out of a run that made its tree, the run asks `removeDirAll` of it (`FullRun`). `FullRun` places that removal after the reading and the gate's build and reload. `FullRun.removal_order`: no event removes a directory, or one does, with no removal before it and only reporting after it, whatever its response; `FullRun.no_remove_before_command` excludes removal before any later Lake command. If the initial allocation fails, it is the first event and only reporting follows. A failed removal changes no verdict.
- **Exit code and last line.** The exit code is a function of the verdict alone, `Regula.Language.Report.exitCode` or `Regula.Closed.Verdict.exitCode`, and so is the last line but for the directory that a pass names at its end, `Regula.Language.Report.labelOn` or `Regula.Closed.Verdict.proofLineOn`. `full_gate_lines`, `proof_verdict_lines` and `pass_lines_name_subject` state each sentence word for word. The last event requests one physical verdict line, and every physical line requested by preceding `println` calls starts with two spaces (`EndsWith`, `IsDetail`). `detailText_no_break` proves that diagnostic serialization escapes LF and CR for every string, and `detailText_guidanceLine` and `say_guidanceLine_spec` state the 2-space-indented `  fix: ...` line emitted beneath each finding via `say`; `serialized_split` relates those physical lines to the concatenated characters, including each LF that `IO.println` appends, and `endsWith_serialized` gives their final-line distinction. These statements concern the checker's requested output: output from Lake's child processes, partial writes and external writers are not `println` events of this trace. A failed print changes nothing the run decides. Exit 0 from the full gate gives all of the above with `lake build --wfail` ending with 0, successful replay of the claim's cone during loading, and the floor of the build (`full_exit_zero`).

- **What a run is about.** For every argument list and every response, a run is a refusal, the proof verdict when `REGULA_FULL` is unset, or the full gate on the directory it names when it is set (`run_subject`), and an argument list other than one word is a refusal (`run_other`). A pass of the proof verdict names the current directory's real path, from which the workspace it read was loaded, and whose search path starts the one that the run got (`SearchPathStarts`, `plainRun_pass`). These state what the run asked and received, and none of them says which workspace Lake selected. That Lake passes on the variable is measured, and that `lakefile.toml` has no key that sets one is read from Lake's source.

**Not vacuous.** A program that does nothing and ends with other than 2 fails the record (`constant_program_fails`), and so does one that reads nothing and refuses everything (`refuser_fails`). `admits_a_project` is conditional: for paths that meet the hypotheses `WitnessPaths`, it gives responses on which the check that runs admits a project. [A pass is owed](#a-pass-is-owed) states the rest. The hypotheses are what the tests of a path give, because `System.FilePath` depends on `System.Platform.isWindows`, an `opaque` constant (`Init/System/Platform.lean:22`, `:39`) that no reduction of the kernel can evaluate; that the pinned text trimmed is itself, on which `decide +kernel` got stuck (**measured**); and that an empty log holds no error, which is read from `Lean/Message.lean:702-703`. No theorem discharges them, and no verdict relies on them: they are hypotheses of the model, not of a run. **Observed**: the gate's run on Regula's own checkout takes the same branches on real paths and ends with `full verdict: pass`.

**The link to the executable.** `interpret_runs` and `executed_meets`, for any table and from any state of the world: what `Prog.interpret` computes is the value of a run whose events are what the program asks, each with the table's answer at the world the run has reached. `BaseIO` is a state monad in Lean's own definition (`Init/System/ST.lean`), so this is a theorem about that definition, and no assumption that effects run in program order. That the compiler keeps that order stays with the compiler.

### A pass is owed

The record requires both relevance and preparation. A reason names something the requested build needs; the exact phase relations constrain every operation whose response depends on the tree that the run writes, including failed attempts, and each operation on a search path names that path. The earlier gap arose because membership in a trace established relevance while permitting inserted acts that could spoil a later operation. Ordered segments now close that gap in the record itself, independently of the owed-pass premises. The following results hold for every program meeting the record, in [`Proofs/Preparation.lean`](RegulaSpecification/Proofs/Preparation.lean) and [`Proofs/Owed.lean`](RegulaSpecification/Proofs/Owed.lean):

- **A non-pass has a defined reason.** `Reason`, `Needed`, `PlainReason`, `TreeReason` and `BuildRejected` are closed. Each case binds its event to the requested build through what the run was told: the answer to `LEAN_SYSROOT`, the real path of the project and of the tree, Lake's load of that tree, the modules of its default targets, a name the build needs (`Named`, each module of a default target and what the file of such a name imports), and that name's file. **Proved**: `manufacturer_fails` excludes the program that reads an unrelated environment variable and reports incomplete; `misjudge_fails` excludes the program that receives a successful `LEAN_SYSROOT` response and reports incomplete without loading; `unrelated_read_no_reason` states that a trace of one event, a failed real path of a path other than the project and the tree, holds no reason. Preparation comes from the same run's phase relations, so none of these relevance predicates alone is the whole contract.
- **Copies cannot manufacture their own preparation.** `ReadingPreparation.first_directory` states that when the first tree act creates a directory, that directory is the TOML destination's parent. `manufacturedCopy_fails` excludes the reported trace that reads the TOML, creates a directory at its destination, fails its write, removes the tree and reports incomplete, for every path, text, error, profile and exit code. Its proof uses the missing toolchain response. `manufacturedCopyAnswered_fails` excludes the same trace with that response present, through the copy grammar: `first_directory` says the directory is the destination's parent, and `parent_ne_self` says that no path is its own parent, on any platform. Each later step needs a named module's file and an earlier source read; a child path that obstructs another named file is therefore a conflict directed by the project's own configuration. `BuildAndRules.no_mutation` and `FullRun.after_removal_saying` exclude later explicit writes and nonterminal removal. No theorem infers filesystem contents from arbitrary response values.
- **A later write takes away the authority of an earlier reading.** `FullRun.gate_stands`: when a full run reaches a Lake command or a load for the rules, it has the form of an admitted reading and a gate, there is a reading inside the closed language with no failed answer on `Evidence` of what the reading leaves, and at each point of the gate, the reload included, what stands is that. `FullRun.at_consumer` and `FullRun.judged_at_consumer` state it at the consumer. `Evidence.judged`: each text standing was judged. `uncheckedCopy_fails`: a trace that ends by reading a file again and copying that text over a file has no `Evidence` of what it leaves, for every text other than the pinned one that neither of Lean's and Lake's parsers was given, and `uncheckedCopy_build_fails` says that no full run reaches a build after it. `moduleCopies_admits_uncheckedCopy` states that the module-copy grammar alone admits that trace, on its premises. Its neighbour `judgedCopy_stands` keeps the evidence when the copy's text is the one standing, and `rewritten_stands` gives what stands after two writes, so a program that writes one text, reads again and judges the later one rests on the later one. `Regula.Reader.twoTexts` refuses, as `incomplete`, what would hold two texts at one path, with `Reason.twoTexts`, because `Evidence` credits one text at each path.
- **What is credited is what the file system answered.** `Regula.Reader.readBack` reads each planned file back, by the path it was written at, after the reader's last write, and stops at a differing or failed answer, read from its code, which is `incomplete` (`readFiles_spec`, `Reason.treeDiffers`). `ReadBack` itself asks for a matching read and does not exclude another read that differs. `FullRun.answered_at_consumer` states it at each consumer. `act_after_readBack_fails`: a reading that ends with an act, for each act of `Op` that is not quiet, fails `ReadBack` once a written text stands. So two paths with different components that the file system takes for one file, by case folding, by Unicode normalization or by anything else, are refused when their texts differ, provided no other process changes the file between the two reads (argued, not proved, and measured for case folding only), and the read-back accepts them when they agree. A read through another string with the same components does not discharge the clause, and `written` still treats such strings as one place. The texts compare as the operations give them: `IO.FS.writeFile` puts a string's bytes and `IO.FS.readFile` gives the bytes it decodes (`Init/System/IO.lean:1058-1060`, `:1229-1233`), so a line ending is compared as it was written. `Reason.treeDiffers` requires the read to come after a successful write of that text at that path, so a run cannot cite a read it asked first.
- **What Lake takes as its configuration.** `Regula.Reader.noOtherConfig` asks the file system for the name `lakefile.lean` in the tree after the read-back, and stops with `incomplete` when anything answers (`Reason.configShadowed`), or when the question fails (`Needed.treeLeanConfig`). `FullRun.config_at_consumer`, on one answer for each real path: at each Lake command and each load for the rules, the reading's last segment holds that no such name answered and that a read through a spelling of `lakefile.toml` in the tree gave the text Lake's parser read. `act_after_readBack_fails` covers an act after it. A project whose module the tree's volume takes for that name, and for which the project's own test found nothing, is refused (**measured**), and on a volume that does not take it for that name it passes (argued). The reading is about what the build consumes at the last read: another process that changes the tree after that answer is not in this statement, and the owner's confirmation leaves it unsaid.
- **A pass is owed under the defined premises.** `PlainOwed` excludes `PlainReason` and a refused replay, and requires the floor of each loaded reading. `FullOwed` excludes allocation failure, admission reasons, build rejection, reload reasons and a refused replay, and requires `BuildAnswer.Floor` of what each loaded build answered. **Proved**: `plain_owed`, `full_owed`, and `run_plain_owed`, `run_full_owed` at the whole run give the pass verdict and exit 0 under these premises. `pass_iff_answer` states the pure part in terms of what Lean and Lake answered, with none of the checker's functions: the loader and the rules pass exactly on `BuildAnswer.Floor`. `loadFloor_iff` relates it to `LoadFloor`, the same requirement over the checker's own reading, and `pass_iff_floor` states the verdict over that. Preparation follows from `PlainRun` and `FullRun` even when these owed-pass premises do not hold. `FullOwed` is the absence of each reason, and says nothing of who else ought to pass: [the closed list](#the-closed-list-of-refusals) says what that means.

### So thin that it only calls Lean
